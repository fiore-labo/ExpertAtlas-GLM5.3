# Expert Atlas: どの選択で expert を並べ替えるか

コントロールパネルの **エキスパート最適化** は、割り当てに含まれる幅（bit 数）の間で routed expert を並べ替えます。モデルがよく選ぶ expert ほど広い bit になり、メモリの量は変わりません。並べる元には、プロンプトを読む間（prefill）に選ばれた expert、token を生成する間（decode）に選ばれた expert、またはその両方を混ぜたものを使えます。このページでは、それぞれの選び方の改善率（3 bit による損失が並べ替えでどれだけ縮むか）を、DGX Spark 上で、8,192 token の文書と 128K・256K token のプロンプトについて測った結果を示します。

## まとめ

- **prefill と decode では、使われる expert が違います。** 174 本のプロンプトで、ある層の prefill でよく選ばれた上位 64 個と decode でよく選ばれた上位 64 個は 42 % が共通でした（でたらめに選べば 25 %）。深い層ほど 2 つの並びは違います。同じプロンプトの prefill と decode の選択は、違う種類の作業の 2 本のプロンプトの prefill どうしよりも似ていません。
- **decode の選択を重くするほど、decode の位置（モデルの返答）の精度が上がります。重み 0.7 あたりまでです。** 8,192 token では、改善率は decode の選択で並べると 25 %、prefill の選択で並べると 13 % でした。128K と 256K token では、decode の重み 0.7 が 34 % と 32 %、prefill の選択だけでは 28 % と 21 % でした。0.5 から先は伸びが小さくなります。
- **prefill の位置（プロンプト）の精度は、重みでほとんど変わりません。** どの重みも改善率は 15〜21 %（8,192 token）、低い値 1 つを除いて 15〜25 %（128K token）、21〜24 %（256K token）で、重みどうしの差は測定のばらつきの範囲でした。
- **そのため、パネルの「両方」は、expert の decode の割合を 0.7、prefill の割合を 0.3 で重みづけします。** decode と prefill は、それぞれ片方だけで並べます。

## 並べ替えの前後の KL: DGX Spark 4 台、3 bit と 4 bit を半分ずつ、重み 0.7

routed expert をすべて 4 bit にしたモデルからの KL ダイバージェンス（そのモデル自身の値は 0）を、採点した位置で平均したものです。並べ替える前（「最適化なし」）と、パネルの「両方」（*w* = 0.7）で並べ替えた後を比べます。改善率 = 1 − KL(*w* = 0.7) / KL(最適化なし) で、3 bit による損失のうち並べ替えで縮んだ割合です。

| プロンプト | 位置 | 最適化なし | *w* = 0.7 | 改善率 |
|---|---|---|---|---|
| 8,192 token | decode | 0.02443 | 0.01848 | 24.4 % |
| 8,192 token | prefill ¹ | 0.02352 | 0.01990 | 15.4 % |
| 128K token | decode ² | 0.01364 | 0.00899 | 34.1 % |
| 128K token | prefill ² | 0.01149 | 0.00964 | 16.1 % |
| 256K token | decode ² | 0.01401 | 0.00949 | 32.3 % |
| 256K token | prefill ² | 0.00412 | 0.00321 | 22.1 % |

¹ 最適化なしの KL が大きい方から 1 % の位置を除いた平均です。単純平均は 0.04273 と 0.04384（−2.6 %）で、数十の位置で決まります。
² どれか 1 つの割り当ての KL で大きい方から 1 % に入る位置（101〜135 位置）を除いた平均です。単純平均は次のとおりです。

| プロンプト | 位置 | 最適化なし | *w* = 0.7 | 改善率 |
|---|---|---|---|---|
| 128K token | decode | 0.02221 | 0.01389 | 37.5 % |
| 128K token | prefill | 0.06075 | 0.04605 | 24.2 % |
| 256K token | decode | 0.02171 | 0.01423 | 34.5 % |
| 256K token | prefill | 0.01635 | 0.01284 | 21.5 % |

以下の結果の割合は、95 % 区間を出すために 32 位置ずつのブロックで計算しており、この表の値と最大 2 ポイント違います。

## 測り方

- **ハードウェアと重み。** DGX Spark、このリリース。routed expert は 3 bit と 4 bit のバンクから半分ずつ（9,600 + 9,600 個、平均 3.5 bit）、それ以外の重みは 8 台用のチェックポイントのものです。
- **割り当て。** 重み *w* ごとに 1 つの割り当てを作ります。expert の点数は、*w* × その層の decode の選択に占める割合 + (1 − *w*) × その層の prefill の選択に占める割合です。ランチャーと同じく全層をまとめて並べ、点数の高い expert に 4 bit を割り当てます。*w* = 0 は prefill の選択で、*w* = 1 は decode の選択で並べることになり、*w* = 0.7 がパネルの「両方」です。「最適化なし」は起動時の割り当てで、各層の中で幅が交互に並びます。
- **並べ替えが学んだもの。** 12 種類の作業（エージェントの会話、コーディング、日本語と英語の文章、Linux の運用、サーバーのセキュリティ。日本語と英語）の 162 本のプロンプトでの選択です。それぞれ 500 token を生成しました。以下の試験の文章はどれも含まれていません。
- **測ったもの。** 次の token の分布の KL ダイバージェンスです。比べる相手は、routed expert をすべて 4 bit にした同じモデルで、文章を teacher forcing で与え、位置ごとに測りました。採点の構成は決定的です（プロンプトの chunk は 2,048 行、プロンプト用の expert カーネルなし、KV キャッシュは FP8）。同じ割り当てなら、何度実行しても同じ logits になります。「改善率」は 1 − KL(割り当て) / KL(最適化なし) で、3 bit の expert による損失のうち並べ替えで縮んだ割合です。95 % 区間は、32 位置ずつのブロックを再標本化して求めました。
- **prefill の位置と decode の位置。** prefill の位置は、モデルに与えた文書の token を予測します（prefill が読む文章）。decode の位置は、その文書に対するモデル自身の返答（思考の文章。温度 0.6 で生成。decode が書く文章）の token を、文書の後に teacher forcing で与えて予測します。どちらも同じ方法で採点しており、名前はその位置がどちらの文章にあるかを示します。文書全体も割り当てどおりの bit で計算するので、decode の位置には、少ない bit で読んだことの影響も含まれます。
- **窓の先頭にチャットテンプレートを置きません。** テンプレートのユーザーの発言の中では、長さに関係なく、モデルはユーザー自身の文章をうまく予測しません（確認では、最も確からしい token が文章と一致したのは約 4 分の 1 の位置でした。テンプレートの冒頭を外すと 96〜98 %）。そのため窓は文書の中から始まり、prefill の位置は、モデルが文書そのものをどれだけ追えるかを表します。

## 結果: 8,192 token の文書、12 種類の作業

DGX Spark 4 台（TP=4。基準も同じ）。学習に使っていない 12 本のプロンプト（作業の種類ごとに 1 本）から、それぞれ 8,192 token の窓を 2 つ作りました。文書の窓はプロンプトの最後の 8,192 token、返答の窓はプロンプトの最後の 7,168 token の後にモデルの返答の最初の 1,024 token を続けたものです。各窓の最後の 1,023 位置を採点し、種類ごとに 12,276 位置になります。

| 割り当て | decode: 改善率 [95 %] | prefill: 改善率 [95 %] |
|---|---|---|
| *w* = 0（prefill） | 13 % [7, 18] | 17 % [1, 25] |
| *w* = 0.2 | 19 % [14, 22] | 21 % [3, 28] |
| *w* = 0.3 | 21 % [16, 25] | 17 % [−2, 27] |
| *w* = 0.4 | 20 % [16, 22] | 19 % [−4, 28] |
| *w* = 0.5 | 19 % [14, 23] | 19 % [5, 26] |
| *w* = 0.7（両方） | 24 % [20, 28] | 15 % [−4, 23] |
| *w* = 1（decode） | 25 % [22, 29] | 16 % [3, 26] |

最適化なしの KL: prefill の位置 0.0427（中央値 0.0016）、decode の位置 0.0244（中央値 0.0044）。prefill の列は、最悪の 1 % の位置を除いています。その位置が prefill の位置の KL の約半分を占め、割り当てごとの変動が大きすぎて、単純な平均では比べられないためです。

## 結果: 128K・256K token のプロンプト、コーディングと Linux の運用

基準（routed expert をすべて 4 bit）は DGX Spark 8 台（TP=8）、各割り当ては 4 台（TP=4）で計算しました。学習に使っていないプロンプトを長さごとに 4 本使いました。コーディングが 2 本（ある言語の標準ライブラリのソースファイルとヘッダー）、Linux の運用が 2 本（マニュアルページ、システムのジャーナル、設定ファイル）で、どれも最後に 1 つの作業の依頼が付きます。それぞれへのモデルの返答は温度 0.6 で生成しました。窓は、チャットテンプレートの冒頭の token を外したプロンプトの後に、返答の最初の 1,024 token を続けたもので、131,062 token（128K）と 262,134 token（256K）です。各窓の最後の 2,047 位置（prefill 約 1,023、decode 1,024）を採点し、長さごとに種類ごとに 4,092〜4,098 位置になります。

prefill・decode とも、どれか 1 つの割り当て（最適化なしを含む）の KL で最悪の 1 % に入る位置を、すべての割り当てで同じように除いています（種類と長さごとに 101〜135 位置）。prefill の位置の単純な平均は数十の位置で決まり、割り当ての間で数十 % 動きます。

**decode の位置: 改善率 [95 %]**

| 割り当て | 128K | 256K |
|---|---|---|
| *w* = 0（prefill） | 28 % [21, 33] | 21 % [17, 26] |
| *w* = 0.3 | 31 % [24, 37] | 29 % [25, 33] |
| *w* = 0.5 | 33 % [27, 38] | 30 % [25, 35] |
| *w* = 0.7（両方） | 34 % [29, 40] | 32 % [28, 36] |
| *w* = 1（decode） | 33 % [27, 39] | 33 % [29, 36] |

**prefill の位置: 改善率 [95 %]**

| 割り当て | 128K | 256K |
|---|---|---|
| *w* = 0（prefill） | 24 % [12, 35] | 24 % [11, 35] |
| *w* = 0.3 | −2 % [−19, 12] | 21 % [6, 33] |
| *w* = 0.5 | 25 % [14, 34] | 23 % [11, 33] |
| *w* = 0.7（両方） | 15 % [1, 27] | 24 % [13, 33] |
| *w* = 1（decode） | 15 % [0, 28] | 24 % [10, 35] |

**最も確からしい token が基準と違う位置の割合**（decode / prefill）

| 割り当て | 128K | 256K |
|---|---|---|
| 最適化なし | 3.8 % / 2.3 % | 4.0 % / 1.2 % |
| *w* = 0（prefill） | 3.1 % / 1.9 % | 3.4 % / 1.0 % |
| *w* = 0.3 | 3.3 % / 2.3 % | 3.4 % / 1.2 % |
| *w* = 0.5 | 3.1 % / 2.2 % | 3.2 % / 0.9 % |
| *w* = 0.7（両方） | 3.0 % / 1.9 % | 3.2 % / 1.0 % |
| *w* = 1（decode） | 3.0 % / 2.2 % | 3.3 % / 1.2 % |

decode の位置では、作業の種類で違いがあります。コーディングは decode の重みとともに最後まで上がり（128K: *w* = 0 で 13 %、0.5 で 18 %、1 で 27 %。256K: 17 %、28 %、30 %）、Linux の運用は 0.3 から横ばいです（128K: 35 %、40 %、37 %。256K: 25 %、32 %、33 %）。prefill の位置の低い値 1 つ（128K の *w* = 0.3）は、256K と 8,192 token では見られません。

## 注意

- 基準は routed expert をすべて 4 bit にしたモデルで、BF16 のモデルではありません。測った損失は、4 bit の expert に対する 3 bit の expert の損失です。
- 128K と 256K では、基準を 8 台、各割り当てを 4 台で計算しました。台数の違いが KL に加える分は、どの割り当ての値にも最適化なしの値にも入っており、それだけを別には測っていません。
- 長いプロンプトは長さごとに 4 本で、作業は 2 種類です。返答は思考の文章で、最終的な回答やツール呼び出しだけを分けては測っていません。
- 並べ替えは与えられた選択から学びます。選択そのものでオフラインに測ると、学習データに無い種類の作業では、得られるはずの改善のうち捉えた割合が小さく、学習データにある作業の約 3 分の 2 でした。
