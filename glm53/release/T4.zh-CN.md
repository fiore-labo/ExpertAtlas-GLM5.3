# 在四台 DGX Spark 上运行完整版 GLM-5.3

发布版本 r3.1-102 不仅能在八台、也能在四台 NVIDIA DGX Spark 系统上提供完整版 GLM-5.3 服务：当 `NODES` 列出四个节点时，同一个归档（`tensorfold-r3.1-102-linux-aarch64.tar.gz`）和启动脚本（`tf-glm53`）以张量并行 4 运行，每个 GB10 一个 rank。四个节点上还可以运行控制面板 Expert Atlas（见下文）。它是 Fiore-lab 基于 TensorFold 1.0.2 制作的非官方衍生版本，并非 TensorFold 项目的发布版本。两种配置共通的内容（NCCL、ssh、各命令、草稿模型、对话缓存、故障处理）见 `RUNTIME.zh-CN.md`；本页说明四节点时的不同之处，以及四节点配置的设置和测量结果。

## 运行方式

- 张量并行 4，解码上下文并行 2（两组，每组两个 rank；每个 rank 隔一个 token 持有 KV 缓存）。
- 提示词按 16,384 行分块，每块分为 4 个 4,096 行的序列并行部分来计算；各部分的部分和通过 ring 归约；路由专家在每个部分中对每个专家的权重只读取并解码一次，用于该部分的所有行。
- KV 缓存为 4 比特（`KV=fp4`）：每个 latent 行有 512 个 e2m1 编码、每 16 个编码一个 e4m3 缩放因子，以及一个 2 的幂次的行缩放因子，这是 MiaAI-Lab 的 GLM-5.3 EXL3 on 3x DGX Spark 项目中 4 比特 latent KV 缓存的格式。每个 16 字节片段中的编码按 sm_121a 上 attention 转置加载的读取顺序存放；attention 将这些行原样放入共享内存，在作为 MMA 操作数时才将编码转换为 e4m3。
- 提示词部分中路由专家的槽位和以 fp16 累加（`TF_GLM53_PE_F16`，默认开启）。
- 对长行，indexer 的 top-k 先读取顺序字的高 16 比特（`TF_GLM53_TOPK16`，默认开启）。

## 每个节点的要求（RUNTIME.zh-CN.md 之外）

- 连接在同一个 RoCE v2 网络上的四台 DGX Spark 系统（每台一个 100 Gb/s 端口即可），第一台能通过 ssh 免密码访问其他节点。
- 四节点检查点（见下文），在每个节点上放在相同路径下：需要 344.6 GB（321 GiB）磁盘空间。
- 启动前每个节点需有 115 GiB 可用内存（不使用 DFlash2 时为 112），以 `free -g` 的显示为准。

## 四节点检查点

Hugging Face 上 Fiore-lab 的 EXL3 检查点 `fiore-lab/GLM-5.3-EXL3-4x-DGX-Sparks`：88 个文件共 344.6 GB，另有 `SHA256SUMS` 和三份模型卡。第 3 至 77 层的路由专家为混合精度：使用最少的 50 %（19,200 个中的 9,600 个，依据智能体工作、编程、Linux 运维和服务器安全方面日语和英语的使用统计选出）为 3 比特，其余为 4 比特。其他部分与八节点检查点 `fiore-lab/GLM-5.3-EXL3-8x-DGX-Sparks` 逐字节相同（包括 MTP 层），专家仍按存储时的 8 个 rank 切分。权重保留其自身的许可证（GLM-5.3 License）。

用 Hugging Face CLI 下载一次（`python3 -m venv` 需要 `python3-venv` 软件包），然后通过 RoCE 网络复制到其他三个节点：

```sh
python3 -m venv ~/hf-cli && ~/hf-cli/bin/pip install -U huggingface_hub
D=~/models/GLM-5.3-EXL3-4x-DGX-Sparks
~/hf-cli/bin/hf download fiore-lab/GLM-5.3-EXL3-4x-DGX-Sparks --local-dir $D
for n in NODE2 NODE3 NODE4; do    # the other three addresses in NODES
  rsync -a --mkpath -e "ssh -c aes128-gcm@openssh.com" $D/ $n:$D/ &
done; wait
```

要校验副本，请在每个节点上运行 `cd ~/models/GLM-5.3-EXL3-4x-DGX-Sparks && sha256sum -c --quiet SHA256SUMS`：每个节点需几分钟，所有文件都一致时不输出任何内容（部署本目录之后，`./tf-glm53 verify` 可一次校验所有节点）。`glm53.t4.conf.example` 中的 `WEIGHTS` 指向该目录。

## 控制面板（Expert Atlas）

r3-102 的新功能，用于四个节点：19,200 个路由专家（第 3 至 77 层，每层 256 个）可以逐个以 2、3、4 或 5 bit 载入，位宽按模型选中该专家的频率逐个决定。控制面板是启动器提供的页面：规划位宽、启动和停止引擎、显示每个 token 选中的专家，并按使用情况重新排序。命令、设置和页面内容见 RUNTIME.zh-CN.md 的“控制面板”一节。

- **bank**：每个 bank 是统一为一种位宽的路由专家，位于 Hugging Face：`fiore-lab/GLM-5.3-EXL3-Experts-2bit`（187.3 GB）、`-3bit`（277.9 GB）、`-4bit`（368.5 GB）和 `-5bit`（459.1 GB），各自附带清单，在每个节点上放在 `expert-plan/banks.json` 指定的目录（`~/models/GLM-5.3-EXL3-Experts-<N>bit`）中。面板只提供每个节点都具备的位宽。
- **检查点**：从面板启动时，只从检查点读取路由专家以外的权重（attention、共享专家、dense 层、嵌入、MTP 层），不读取任何路由专家：路由专家全部来自 bank。四节点检查点自身的 3 / 4 bit 混合不会被面板使用；不经面板的 `./tf-glm53 up` 仍像以前一样载入它。八节点检查点的其他权重相同，其路由专家与 4 bit bank 逐个文件相同，因此它的目录可以同时作为 `WEIGHTS` 和 4 bit bank（见 RUNTIME.zh-CN.md 的“控制面板”）。
- **内存**：路由专家占用节点的大部分内存，因此它们的位宽决定了 KV 缓存还剩多少。以下是四个节点在不运行其他程序、实测启动一次之后、使用下文设置（`KV=fp4`、`STORE=100000`、MTP 草稿模型）时启动器的计划：

| 路由专家 | 判定 | 上下文（4 bit KV 缓存） |
|---|---|---|
| 全部 3 bit | 可容纳 | 737,280（完整的 `CONTEXT`） |
| 一半 3 bit、一半 4 bit | 可容纳 | 737,280（每个节点约余 7.5 GiB） |
| 70 % 为 3 bit、30 % 为 4 bit（`CONTEXT` 1,048,576，`STORE` 512） | 可容纳 | 1,048,576（每个节点约余 7.5 GiB；实测了 1,019,186 个 token 的提示词和运行中的重排） |
| 四分之一 3 bit、四分之三 4 bit | 可容纳 | 622,592 |
| 全部 4 bit | 可容纳 | 327,680 |
| 全部 5 bit | 无法容纳 | - |

  使用 DFlash2 时每个节点多用约 4 GiB，上下文会更短（一半 3 bit、一半 4 bit 时为 638,976）。若要在含 4 bit 专家的同时保持完整上下文，除了 4 bit bank 之外还需要 3 bit bank；2 bit 和 5 bit 可选。还没有任何运行时，面板的计划为可容纳的全部 3 bit。在相同内存下，含 2 bit 专家的配置比不含的配置离基准远 13% 至 30%；把其他专家降到 3 bit 来换取 5 bit 专家，没有可测出的改善（测量值见各 bank 的模型卡）。
- **磁盘**（每个节点）：四节点检查点加 3 bit 和 4 bit bank 共 991 GB；若以八节点检查点作为 4 bit bank 再加 3 bit bank，则为 668 GB。

## 设置

`glm53.t4.conf.example` 中是四节点的设置。将其复制为 `glm53.conf`，设置地址、网络名称和路径，然后按 RUNTIME.zh-CN.md 的说明启动：

```sh
cp glm53.t4.conf.example glm53.conf    # nodes, network names, NCCL, weights, drafter, port
./tf-glm53 deploy                      # the same directory on the other three nodes
./tf-glm53 up                          # checks, starts the ranks, waits, runs the smoke test
```

| 设置 | 值 | 含义 |
|---|---|---|
| `NODES` | 四个地址 | rank 0 在最前 |
| `WEIGHTS` | `~/models/GLM-5.3-EXL3-4x-DGX-Sparks` | 四节点检查点 |
| `DCP` | 2 | 解码上下文并行 |
| `ROWS` / `SP_PARTS` | 16384 / 4 | 提示词分块的行数、每块的部分数 |
| `CONTEXT` | 737280 | 单个请求最多可达到的token 数（提示词 + 回复） |
| `STORE` | 100000 | 在 `CONTEXT` 之外为先前对话保留的token 数 |
| `CACHE` | `pool` | KV 池（见下文） |
| `KV` | `fp4` | 4 比特 KV 缓存 |
| `DRAFTER_KIND` | `mtp`（默认）或 `dflash2` | 见下文“草稿模型与许可证” |

## 请求之间保留的对话

四节点在 KV 池（`CACHE=pool`）中保留对话，KV 池的说明见 RUNTIME.zh-CN.md。按上面的值，它以 256 个 token为一块，共持有 `CONTEXT` + `STORE` = 837,280 个 token，由所有对话共享：

- 请求从任一对话中已缓存的最长前缀处继续，而不仅限于紧接其前的对话。
- 开头相同的对话（同一个系统提示词）只持有一份共同的块。
- 池满时，最久未使用的对话从其末尾开始交出块。
- 使用 DFlash2 时，最多保留 8 个对话的草稿模型状态（`DRAFT_SAVES`）。

使用 DFlash2 时，最低可用内存为每个节点约 3.2 GiB（512K 时），比相同取值下的槽位缓存（`CACHE=slots`）少约 0.5 GiB。

## 速度

**测量时每个节点的 GPU 时钟上限均设为 2.1 GHz（2,100 MHz）。** 使用没有已缓存前缀的编程提示词，一次一个请求（reasoning effort 为 low，回复最多 4,000 个 token），采用上面的设置；取两次运行的中位数。

| 提示词 | 首 token 时间，MTP / DFlash2（s） | MTP 解码（tokens/s） | DFlash2 解码（tokens/s） |
|---|---|---|---|
| 129,438 token（128K） | 120.1 / 121.9 | 35.3 | 42.9 |
| 260,227 token（256K） | 253.3 / 256.9 | 33.2 | 40.7 |
| 529,885 token（512K） | 565.4 / 571.5 | 32.2 | 37.8 |

一个 703,916 token 的对话再次发送时，从池中继续了 703,899 个 token，首 token 时间不到 3 秒；中间插入另一个对话的简短提问之后也是如此。

## 精度

相对于官方 BF16 模型（以官方实现运行官方权重、以 FP32 计算）输出分布的 KL 散度：基于参考数据的四个 8,192 token 窗口，按token 区间，在确定性配置下使用本检查点和 4 比特 KV 缓存测得。

| token | 4 比特 KV 缓存（本配置） | 8 比特 KV 缓存 |
|---|---|---|
| 1,024 至 2,047 | 0.0190 | 0.0156 |
| 2,048 至 4,095 | 0.0316 | 0.0258 |
| 4,096 至 6,143 | 0.0289 | 0.0259 |
| 6,144 至 8,190 | 0.0192 | 0.0160 |

- 混合检查点和 4 比特 KV 缓存是权重和缓存本身的近似，分别测量：相对于 4 比特检查点，混合检查点增加的散度为全 3 比特检查点所增加散度的 36 % 至 58 %；4 比特 KV 缓存相对于 8 比特增加 0.003 至 0.005。
- 除 fp16 槽位和之外，四节点配置的每项加速都与不使用时给出相同的比特：rank 0 在参考窗口上的 logits（确定性配置，ring 和 reduce-scatter，4 比特和 8 比特 KV）在使用与不使用时 MD5 相同；对于 top-k 的读取方式，131,072 token 的 teacher forcing 运行同样一致。
- fp16 槽位和不改变散度：0.0161 / 0.0239 / 0.0244 / 0.0166，fp32 累加时为 0.0167 / 0.0234 / 0.0252 / 0.0172（相同窗口，八节点检查点，4 比特 KV）。

## 草稿模型与许可证

两种草稿模型都可在四节点上使用（RUNTIME.zh-CN.md 的“草稿模型”一节）：

- `mtp`（默认）：检查点自带的 MTP 层，属于 GLM-5.3 权重的一部分，适用其许可证。
- `dflash2`：`incoai/GLM-5.3-DFlash2`，本归档不包含。其模型卡注明的许可证为 CC BY-NC-ND 4.0（非商业性使用，禁止演绎），用途为研究和评估，商业许可可向 Inco AI 获取。获取和使用方法见 RUNTIME.zh-CN.md。某个部署的使用是否在许可范围内，由其运营者自行判断。

## 限制

- 单个请求最多达到 `CONTEXT` 个 token（提示词与回复合计）：733,226 token 的提示词只给回复留下约 4,000 个 token。
- 一次只运行一个请求，如 RUNTIME.zh-CN.md 所述。
- 这四个节点上不运行其他任何程序：内存只按本服务器单独估算。
