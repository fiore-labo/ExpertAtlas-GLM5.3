# Full GLM-5.3 on four DGX Sparks

Release r3.3.6-102 serves full GLM-5.3 on four NVIDIA DGX Spark systems as well as on eight: the same archive
(`tensorfold-r3.3.6-102-linux-aarch64.tar.gz`) and launcher (`tf-glm53`) run tensor parallelism 4, one rank per GB10, when
`NODES` lists four nodes. On four nodes it also runs the control panel, Expert Atlas (below). It is Fiore-lab's unofficial derivative of TensorFold 1.0.2, not a release of the TensorFold
project. `RUNTIME.md` covers everything common to both (NCCL, ssh, the commands, drafters, the conversation cache,
failures); this page gives what differs with four nodes, and the settings and measurements of the four-node form.
`RING.md` gives four nodes cabled as a ring without a switch.

## How it runs

- Tensor parallelism 4, decode context parallelism 2 (two groups of two ranks, each rank holding every other position
  of the KV cache).
- Prompts in chunks of 8,192 rows, each run as 4 sequence-parallel parts of 2,048 rows; the parts' partial sums
  reduced over a ring; the routed experts of a part read and decode each expert's weights once for all its rows.
- KV cache in 4 bits (`KV=fp4`): 512 e2m1 codes a latent row with an e4m3 scale for each 16 and a power-of-two row
  scale, the layout of MiaAI-Lab's 4-bit latent KV cache from their GLM-5.3 EXL3 on 3x DGX Spark project. The codes of
  each 16-byte piece are stored in the order the attention's transposed loads read on sm_121a; the attention keeps
  these rows as they are in shared memory and turns codes into e4m3 at the MMA operands.
- The routed experts' slot sums of a prompt part are added in fp16 (`TF_GLM53_PE_F16`, on by default).
- The indexer's top-k of long rows reads the order words' top 16 bits first (`TF_GLM53_TOPK16`, on by default).

## What each node needs (beyond RUNTIME.md)

- Four DGX Spark systems on one RoCE v2 network (one 100 Gb/s port each is enough), or cabled as a ring (`RING.md`), the
  first reaching the others over ssh without a password, their host keys already known (`QUICKSTART.md`, section 1).
- The Base weights (below) and the 3-bit bank at the same path on every node: 21.2 GB (19.8 GiB) and 277.9 GB of disk,
  299.1 GB together. Every start needs both.
- Memory available on every node before `tf-glm53 start`, as `free -g` shows it: 101 GiB with the example's `KV_SIZE` (104 with DFlash2). A start from the control panel asks what its plan needs.

## The weights

Fiore-lab's `fiore-lab/GLM-5.3-EXL3-Base` on Hugging Face: 21.2 GB (19.8 GiB) in 13 files, everything but the routed experts of layers 3 to 77,
which a start reads from the banks. It is the same on four nodes and on eight. The weights keep their own license (GLM-5.3 License).

The full checkpoint `fiore-lab/GLM-5.3-EXL3-4x-DGX-Sparks` (344.6 GB in 88 files, plus `SHA256SUMS` and three model cards) holds those experts as well, and a
start does not need them. If you have it, name it with `WEIGHTS` and it works as it is. Its routed experts are mixed: the least used 50 % of them (9,600
of 19,200, chosen from usage statistics across agent work, coding, Linux operations and server security, in Japanese
and English) at 3 bits, the rest at 4 bits. Everything else is byte for byte the eight-node checkpoint
`fiore-lab/GLM-5.3-EXL3-8x-DGX-Sparks`, its MTP layer included, and the experts stay cut for 8 ranks as stored.

Download the Base weights once with the Hugging Face CLI (`python3 -m venv` needs the `python3-venv` package), then copy them to the
other three nodes over the RoCE network:

```sh
python3 -m venv ~/hf-cli && ~/hf-cli/bin/pip install -U huggingface_hub
D=~/models/GLM-5.3-EXL3-Base
~/hf-cli/bin/hf download fiore-lab/GLM-5.3-EXL3-Base --local-dir $D
for n in NODE2 NODE3 NODE4; do    # the other three addresses in NODES
  rsync -a --mkpath -e "ssh -c aes128-gcm@openssh.com" $D/ $n:$D/ &
done; wait
```

To check the copies, run `cd ~/models/GLM-5.3-EXL3-Base && sha256sum -c --quiet SHA256SUMS` on every node:
a few minutes each, silent when every file matches (or, once this directory is deployed, `./tf-glm53 verify` does it
on every node at once). `WEIGHTS` in `glm53.t4.conf.example` names this directory.

## The control panel (Expert Atlas)

Each of the 19,200 routed experts (layers 3 to 77, 256 a layer) can be loaded at 2, 3, 4 or 5 bits, chosen expert by
expert from how often the model picks it; a start with no plan loads every expert at 3 bits. The launcher serves the control panel, a page
that plans the widths, starts and stops the engine, shows the experts each token picks and re-sorts them by use;
RUNTIME.md, "The control panel", gives the commands, the settings and what the page shows.

- **The banks.** The routed experts at one width each, on Hugging Face: `fiore-lab/GLM-5.3-EXL3-Experts-2bit`
  (187.3 GB), `-3bit` (277.9 GB), `-4bit` (368.5 GB) and `-5bit` (459.1 GB), each with its manifest, in the directory
  `expert-plan/banks.json` names on every node (`~/models/GLM-5.3-EXL3-Experts-<N>bit`). The panel offers only the
  widths every node holds.
- **The weights.** A start from the panel reads the other weights (attention, shared experts, dense layers, embeddings,
  the MTP layer) from `WEIGHTS` and every routed expert from the banks. With a full checkpoint as `WEIGHTS` its routed experts are not read, nor the four-node
  checkpoint's own 3 / 4-bit mix.
  The eight-node checkpoint has the same other weights, and its routed experts are the 4-bit bank file for file, so
  its directory can serve as both `WEIGHTS` and the 4-bit bank (RUNTIME.md, "The control panel").
- **Memory.** The routed experts take most of a node, so their widths set the KV cache left. The launcher's plans on
  four nodes with nothing else running, after a measured start, with the settings of that time (`KV=fp4`, a context length of at most 737,280, a KV size of the
  context length + 100,000, the MTP drafter, `ROWS` 16,384). The default of 8,192 leaves more memory; the plans have not been worked out again:

| Routed experts | Verdict | Context length (4-bit KV cache) |
|---|---|---|
| all at 3 bits | can start | 737,280 (all it was asked) |
| half at 3 bits, half at 4 bits | can start | 737,280 (about 7.5 GiB a node to spare) |
| 70 % at 3 bits, 30 % at 4 bits, with `CONTEXT_LENGTH` 1,048,576 and `KV_SIZE` 1,049,088 | can start | 1,048,576 (about 7.5 GiB a node to spare; a 1,019,186-token prompt and a live re-sort measured) |
| a quarter at 3 bits, three quarters at 4 bits | can start | 622,592 |
| all at 4 bits | can start | 327,680 |
| all at 5 bits | not enough memory | - |

  Measured for this release (four nodes on a switch, every expert at 3 bits, `KV=fp4`, `CONTEXT_LENGTH` 737,280): `docker run ... IMAGE up` took a KV size of 1,671,168 at the default `ROWS` 8,192 and 1,081,344 at `ROWS` 32,768, with 5.8 to 6.9 GiB a node free after the start.

  With DFlash2 the launcher plans about 3 GiB more a node (its model and work, against the MTP layer's), so near the
  memory's limit a plan's context length is shorter. The full context length with 4-bit experts in it needs the 3-bit bank as well as the 4-bit one; 2 and 5
  bits are optional. Before any run the panel's plan is all 3 bits, which fits. At the same memory,
  a mix with 2-bit experts was 13 to 30 % further from the reference than one without, and 5-bit experts paid for by
  moving others down to 3 bits gained nothing measurable (the banks' model cards give the measurements).
- **Disk** on every node: the Base weights and the 3-bit bank, which are always needed, 299.1 GB; with the 4-bit bank, 667.6 GB; or the eight-node checkpoint
  as `WEIGHTS` and the 4-bit bank with the 3-bit bank, 668 GB.

## Settings

`glm53.t4.conf.example` holds the four-node settings. Copy it to `glm53.conf`, set the addresses, the network names
and the paths, and start as RUNTIME.md describes:

```sh
cp glm53.t4.conf.example glm53.conf    # nodes, network names, NCCL, weights, drafter, port
./tf-glm53 deploy                      # the same directory on the other three nodes
./tf-glm53 up                          # the control panel: open the address it prints, start the engine there
./tf-glm53 start                       # or without the page: every expert at 3 bits, then the last start's plan
```

| Setting | Value | Meaning |
|---|---|---|
| `NODES` | four addresses | rank 0 first |
| `WEIGHTS` | `~/models/GLM-5.3-EXL3-Base` | the Base weights |
| `DCP` | 2 | decode context parallelism |
| `ROWS` / `SP_PARTS` | 8192 / 4 | prompt chunk rows, parts a chunk |
| `CONTEXT_LENGTH` | 1048576 | the context length: positions one request may reach (prompt + reply) |
| `KV_SIZE` | 1049088 | the KV size: the whole KV pool in positions, shared by every conversation. Here `CONTEXT_LENGTH` + 512, the least the pool takes; `docker run ... up` and a start from the panel give it all the room left, unless a KV size is typed on the panel |
| `KV` | `fp4` | the 4-bit KV cache |
| `DRAFTER_KIND` | `mtp` (default) or `dflash2` | see "Drafters and licenses" below |

`glm53.nodes.conf`, which the node check writes, is read after `glm53.conf` and wins for `NODES` and the network names.
An older `glm53.conf` is still read: `CONTEXT` as `CONTEXT_LENGTH`, `CONTEXT` + `STORE` as `KV_SIZE` (`CONFIG.md`).

## Conversations kept between requests

Four nodes keep conversations in the KV pool, which RUNTIME.md describes. It
holds `KV_SIZE` positions in blocks of 256, shared by every conversation (by default all the room left, with `docker run ... up` or a start from the panel); a request reaches at most
`CONTEXT_LENGTH` of them, and earlier conversations stay in whatever blocks are free:

- A request resumes from the longest cached prefix of any conversation, not only of the one just before it.
- Conversations that start alike (one system prompt) hold their common blocks once.
- When the pool is full, the least recently used conversations give up blocks from their ends.
- With DFlash2 the drafter state of up to 8 conversations is kept (`DRAFT_SAVES`).

With DFlash2 the lowest free memory was about 3.2 GiB a node, at 512K and `ROWS` 16,384.

## Speed

**Measured with release r2-102 and the four-node checkpoint's own widths, half at 3 and half at 4 bits, with the GPU clock
capped at 2.1 GHz (2,100 MHz) on every node.** The engine has changed since and a start now loads every expert at 3 bits
by default; these numbers have not been measured again for this release. A coding prompt with no cached prefix, one
request at a time (reasoning effort low, up to 4,000 reply tokens), the settings above but for `ROWS`, which was 16,384 then and is 8,192 now; median of two runs. Speeds differ with the environment (the checkpoint, the prompt, the clocks): take these numbers as a guide.

| Prompt | Time to first token, MTP / DFlash2 (s) | Decode with MTP (tokens/s) | Decode with DFlash2 (tokens/s) |
|---|---|---|---|
| 129,438 tokens (128K) | 120.1 / 121.9 | 35.3 | 42.9 |
| 260,227 tokens (256K) | 253.3 / 256.9 | 33.2 | 40.7 |
| 529,885 tokens (512K) | 565.4 / 571.5 | 32.2 | 37.8 |

Measured for this release, the prefill at each `ROWS`: 1,054 tokens/s at 8,192, 1,102 at 16,384 and 1,110 at 32,768 (four nodes, every expert at 3 bits, the 4-bit KV cache with a small KV, an 81K-token prompt, one run each). With so few runs, take these as a reference.

A conversation of 703,916 tokens sent again resumed 703,899 positions from the pool and gave its first token in under
3 s, also after a short question of another conversation in between.

## Accuracy

KL divergence of the output distributions from the official BF16 model's (the official weights run by the official
implementation, computed in FP32), over the four 8,192-token windows of the reference, by position range; measured in
the deterministic configuration with the four-node checkpoint and the 4-bit KV cache:

| Positions | 4-bit KV cache | 8-bit KV cache |
|---|---|---|
| 1,024 to 2,047 | 0.0190 | 0.0156 |
| 2,048 to 4,095 | 0.0316 | 0.0258 |
| 4,096 to 6,143 | 0.0289 | 0.0259 |
| 6,144 to 8,190 | 0.0192 | 0.0160 |

- The mixed checkpoint and the 4-bit KV cache are the weights' and the cache's own approximations, measured
  separately: the mix adds 36 to 58 % of the divergence that an all-3-bit checkpoint adds over the 4-bit one, and the
  4-bit KV cache adds 0.003 to 0.005 over the 8-bit one.
- Every speed path of the four-node form except the fp16 slot sums gives the same bits as without it: rank 0's logits
  of the reference windows (deterministic configuration, ring and reduce-scatter, 4-bit and 8-bit KV) have the same
  MD5 with and without each, and a 131,072-token teacher-forced run likewise for the top-k reading.
- The fp16 slot sums leave the divergence unchanged: 0.0161 / 0.0239 / 0.0244 / 0.0166 against 0.0167 / 0.0234 /
  0.0252 / 0.0172 with fp32 sums (the same windows, the eight-node checkpoint, 4-bit KV).

## Drafters and licenses

Both drafters work on four nodes (RUNTIME.md, "Drafters"):

- `mtp` (default): the MTP layer in the weights, part of the GLM-5.3 weights and under their license.
- `dflash2`: `incoai/GLM-5.3-DFlash2`, not included. Its model card states CC BY-NC-ND 4.0 (non-commercial use, no
  derivatives), for research and evaluation, with commercial licensing from Inco AI; see RUNTIME.md, "Using DFlash2".
  Whether a deployment's use is covered is for its operator to judge.

## Limits

- A request reaches at most `CONTEXT_LENGTH` positions, prompt and reply together: a 733,226-token prompt leaves room
  for about 4,000 reply tokens.
- By default one request at a time; `MULTI` decodes up to four together (RUNTIME.md, "Several conversations at once").
- The four nodes run nothing else: memory is sized for this server alone.
