# AI アシスタント向けガイド: DGX Spark で動かすフルサイズの GLM-5.3（リリース r3-102）

このページは、システム全体を 1 か所にまとめたものです: これが何か、各部分が何をするか、どう使うか、何ができて何ができないか。利用者がこのリリースを理解する、インストールする、動かす、不具合を切り分けるのを手伝う AI アシスタント向けに書いていますが、人が読んでも同じ内容です。数値は他のページから取っています。詳細はそれらのページにあり、このページより詳しく書いています: `RUNTIME.ja.md`（動かし方。4 台と 8 台の両方）、`T4.ja.md`（4 台）、`PANEL-GUIDE.ja.md`（コントロールパネルの画面）、`ATLAS-TESTS.ja.md`（expert の並べ替えの測定）。ソースのリポジトリでは `packaging/RUNTIME.ja.md`、`glm53/release/T4.ja.md`、`glm53/release/PANEL-GUIDE.ja.md`、`glm53/release/ATLAS-TESTS.ja.md` です。英語版（`AI-GUIDE.md`）が原文です。

## 1. これは何か

フルサイズの GLM-5.3 モデル（755B パラメータ、アーキテクチャ `glm_moe_dsa`）を、NVIDIA DGX Spark（GB10 を 1 基ずつ）4 台または 8 台で、GB10 1 基につき 1 ランク、テンソル並列 4 または 8 で動かすサーバーです。TensorFold 1.0.2（Zig と素の CUDA カーネルで書かれたエンジン）から Fiore-lab が作った非公式の派生物であり、TensorFold プロジェクトのリリースではありません。サーバーは実行時に Python を必要としません。

| 項目 | 値 |
|---|---|
| モデル | フルサイズの GLM-5.3。Fiore-lab が Hugging Face で公開している EXL3 量子化チェックポイント |
| ノード | DGX Spark（GB10）4 台または 8 台を 1 つの RoCE v2 ネットワークに。それ以外には対応しません |
| 文脈 | 最大 1,048,576 トークン。メモリで決まります: 8 台で 1,048,576（FP8 KV、`STORE` 589,824）、4 台で 819,200（4 ビット KV、`STORE` 18,080）。設定例は 819,200 と 737,280 です |
| API | OpenAI 互換の chat API（`/v1/chat/completions`）。既定は `127.0.0.1:8000` |
| リクエスト | 同時に実行するのは 1 件。さらに 32 件まで待ち行列で待ちます |
| drafter | MTP（チェックポイント自身の層。既定）、DFlash2（任意。同梱せず、別のライセンス）、なし |
| コントロールパネル | 「Expert Atlas」: expert ごとの bit 幅（2/3/4/5 ビット）を決める Web ページ。4 台または 8 台 |
| 配布の形 | コンテナイメージ（おすすめ）と、同じファイルのアーカイブ。どちらも Linux aarch64 用 |
| ライセンス | コードは Apache-2.0。重みは GLM-5.3 License のまま。DFlash2 は独自のライセンス（CC BY-NC-ND 4.0）のまま |

## 3. 仕組みの要点

- **ランク。** GB10 1 基に 1 プロセス（ランク）。ランク 0 は `NODES` の 1 台目で動き、HTTP API を提供します。テンソル並列は各層をランクに分け、KV キャッシュはランクの組に分けます（decode の文脈並列、`DCP=2`）。
- **prefill と decode。** プロンプトはチャンクに分けて読み（prefill）、応答は 1 トークンずつ生成します（decode）。prefill の速さは計算で、decode の速さはメモリ帯域で決まります。
- **ドラフト。** decode の各ラウンドで drafter が数トークンを提案し、モデルが 1 ステップでそれを確かめます。モデル自身が選ぶトークンだけを残すので、どちらでも応答はモデル自身のものです。
- **会話のキャッシュ。** `CACHE=pool`（既定）では、`CONTEXT` + `STORE` 位置の KV を 256 位置ずつのブロックに分けた 1 つのプールを、すべての会話で共有します。リクエストは、どの会話のものであってもキャッシュにある最も長い先頭部分から再開し、同じように始まる会話（同じシステムプロンプト）は共通のブロックを 1 回だけ保持します。キャッシュにあるブロックは再利用の前にリクエストのトークンと照合し、少しでも疑わしければすべての会話を捨ててリクエストを最初から計算します（「cold」）。ブロックを誤って再利用することはありません。
- **expert。** GLM-5.3 は層 3〜77 のそれぞれに 256 個の routed expert（合計 19,200 個）を持ち、トークンごとに層あたり 8 個を選びます。チェックポイントはこれを量子化して持ちます: 8 台用はすべて 4 ビット、4 台用は半分（使われる回数の少ない方）を 3 ビット、残りの半分を 4 ビット。コントロールパネルでは expert ごとに別の幅で読めます。

## 4. 2 通りの動かし方

| | `./tf-glm53 up` | コントロールパネル（`./tf-glm53 launcher`） |
|---|---|---|
| ノード | 4 台または 8 台 | 4 台または 8 台（起動画面で選ぶ） |
| expert の幅 | チェックポイントに入っているまま | バンク（2、3、4、5 ビット）から expert ごとに選ぶ |
| 必要なもの | チェックポイント | チェックポイント（expert 以外の重み）と、使う幅のバンク |
| 操作 | コマンドライン | Web ページ（起動、停止、計画、稼働中の表示、エキスパート最適化） |

どちらも同じ `glm53.conf`、同じサーバー、同じ API を使います。

### コンテナで動かす（おすすめ）

`glm53.conf` に `RUNTIME=docker` と `IMAGE` を設定すると、`tf-glm53` は各ランクをリリースのイメージのコンテナとして各ノードで起動します（1 ランクに 1 コンテナ。1 台目から ssh で）。各ノードに要るのは、cuBLAS・libibverbs・NCCL の代わりに Docker と NVIDIA Container Toolkit で（DGX OS には両方あります）、下の手順 1 と 2 は要りません。各ノードでイメージを `docker pull` し（または `./tf-glm53 pull`）、1 台目で `docker run --rm --user "$(id -u):$(id -g)" -v "$PWD/glm53":/out IMAGE install /out` でリリースのファイルをディレクトリに書き、手順 4 から進めます。重みとバンクはホストに置いたまま、読み取り専用でマウントします。詳細は `RUNTIME.ja.md`「コンテナで動かす」にあります。イメージはアーカイブから作ることもできます（`docker/Dockerfile`）。

### 準備（共通）

1. 全ノード: DGX OS（Ubuntu 24.04）、NVIDIA ドライバ 580 以降、cuBLAS 13（`libcublas-13-0`）、`libibverbs`。ノードは 1 つの RoCE v2 ネットワークにつなぎ、1 台目から全ノードにパスワードなしの ssh が通ること。
2. 全ノードに NCCL 2.30.7: `pip3 install --no-deps --target ~/nccl-2.30.7 nvidia-nccl-cu13==2.30.7`（pip はライブラリを展開するだけで、Python は何も実行しません）。
3. チェックポイントを全ノードの同じパスに: `fiore-lab/GLM-5.3-EXL3-8x-DGX-Sparks`（390 GB、8 台）または `fiore-lab/GLM-5.3-EXL3-4x-DGX-Sparks`（344.6 GB、4 台）。Hugging Face の CLI で 1 回ダウンロードし、`rsync` で他のノードにコピーし、`./tf-glm53 verify` で確認します。
4. 1 台目のノードでアーカイブを展開し、`sha256sum -c SHA256SUMS`、合う方の設定例を `glm53.conf` にコピーして、`NODES`、`SOCKET_IFNAME`、`IB_HCA`、`NCCL_LIB`、`WEIGHTS` を設定します。
5. `./tf-glm53 deploy`（このディレクトリを他のノードにコピー）、続いて `./tf-glm53 up`（全ノードを確認し、ランクを起動し、サーバーを待ち、スモークテストを実行）。ローカルの NVMe ドライブからの起動は約 2 分半です。
6. `./tf-glm53 down` で全ランクを止めます。

### コントロールパネルの準備

1. 計画で使う expert バンクを、全ノードの `expert-plan/banks.json` が示すディレクトリ（既定は `~/models/GLM-5.3-EXL3-Experts-<N>bit`）に置きます: 4 台では通常 `fiore-lab/GLM-5.3-EXL3-Experts-3bit` と `-4bit`（277.9 GB と 368.5 GB）。`-2bit`（187.3 GB）と `-5bit`（459.1 GB）は任意です。8 台用のチェックポイントは 4 ビットのバンクとして使えます（`RUNTIME.ja.md`「コントロールパネル（Expert Atlas）」）。`./tf-glm53 verify-banks 3 4` で確認します。
2. 1 台目のノードで `./tf-glm53 launcher` を実行し、そこで `http://127.0.0.1:8010/panel` を開きます（`LAUNCHER_PORT` が無ければポートは `PORT` + 10）。または、ポートを転送します（`ssh -L 8010:127.0.0.1:8010 FIRST-NODE`）。ループバック以外で使うには `LAUNCHER_HOST` と `API_KEY_FILE` が必要で、ページはキーをアドレスから 1 回受け取ります（`/panel#key=KEY`）。ランチャーはエンジンが動いていてもいなくても動き続け、ページはランチャーを通してエンジンに届きます。
3. ページで: 計画、KV の形式、文脈、STORE、各ノードが OS に残す量、drafter を選び、メモリの判定を確かめ、「起動」を 2 回（起動 → 確定）押します。停止もページから行います。

## 5. 設定（`glm53.conf`）

| 設定 | 意味 | 8 台の例 / 4 台の例 |
|---|---|---|
| `NODES` | RoCE ネットワーク上のノードのアドレス。ランク 0 が先頭 | 8 / 4 個のアドレス |
| `SOCKET_IFNAME`、`IB_HCA`、`GID_INDEX` | 全ノードでのそのネットワークのインターフェースと RDMA デバイス、GID の番号（空なら自動選択） | 同じ |
| `NCCL_LIB` | NCCL 2.30.7 の `libnccl.so.2`。全ノードで同じパス | 同じ |
| `WEIGHTS` | チェックポイントのディレクトリ。全ノードで同じパス | 8x / 4x のチェックポイント |
| `DRAFTER_KIND`、`MTP_K`、`DRAFTER` | drafter（`mtp`、`dflash2`、`none`）、MTP の 1 ラウンドのドラフト数（3）、DFlash2 のディレクトリ | `mtp`、3、空 |
| `NAME`、`HOST`、`PORT`、`API_KEY_FILE` | API でのモデル名、待ち受けのアドレスとポート、キーのファイル | `glm-5.3`、`127.0.0.1`、8000、空 |
| `METRICS_LISTEN` | `/metrics` と `/health` だけにキーなしで答える、読み取り専用の追加のアドレス | 無効 |
| `CONTEXT` | 1 件のリクエストが届く位置の数（プロンプトと応答の合計） | 819,200 / 737,280 |
| `STORE` | 以前の会話のために `CONTEXT` とは別に残す位置の数（プールでは 512 以上） | 819,200 / 100,000 |
| `CACHE` | `pool`（ブロックを共有）または `slots`（会話ごとの保存） | `pool` |
| `KV` | KV キャッシュの形式、`fp8` または `fp4`（4 台では `fp4` が必要） | `fp8` / `fp4` |
| `DCP`、`ROWS`、`SP_PARTS` | decode の文脈並列、プロンプトのチャンクの行数、チャンクを分けるシーケンス並列の数 | 2、8,192、4 / 2、16,384、4 |
| `NEED_GB` | 起動前に各ノードで使えるべきメモリ（`STORE` が 819,200 より 100,000 少ないごとに 2.7 GiB 減、DFlash2 では 3 増） | 112（既定）/ 131（112 GiB を要求） |
| `MASTER_PORT`、`READY_TIMEOUT` | ランクが落ち合うポート、サーバーを待つ秒数 | 29551、900 |
| `RUNTIME`、`IMAGE` | ランクの動かし方: `host`（既定。このディレクトリから）か `docker`（それぞれ `IMAGE` のコンテナで） | `host`、空 |
| `EXTRA_ENV` | エンジンの変数。たとえば `TF_GLM53_MULTI=4`（複数の会話をまとめて decode。既定は無効） | 空 |
| `LAUNCHER_HOST`、`LAUNCHER_PORT`、`ATLAS_DIR`、`RESERVE_GB` | コントロールパネル: アドレス、ポート、保存した配分の置き場所、OS に残すメモリ | 4 台の例: `127.0.0.1`、8010、`atlas/`、4 |

## 6. コマンド（`./tf-glm53`、1 台目のノードで実行）

| コマンド | 内容 |
|---|---|
| `deploy` | このディレクトリを全ノード（同じパス）にコピーし、そこで `SHA256SUMS` を確かめます |
| `check` | ノード、ファイル、重み、ライブラリ、RDMA デバイス、GPU、メモリを確かめ、問題を `NG:` の後に並べます |
| `verify` | 全ノードで重みを `SHA256SUMS` と照合します（数分） |
| `verify-banks [BITS...]` | expert バンクのファイルを manifest と照合します |
| `up` | `check` の後、ランクを（最後から先頭へ）起動し、サーバーを待ち、スモークテストを実行します |
| `down` | 全ランクを止めます（TERM、30 秒後に KILL） |
| `status` | ランク、空きメモリ、drafter、会話のキャッシュ、サーバーの `/health` |
| `smoke` | 答えを確かめる 3 件のリクエスト |
| `logs [R]` | ランク R のログを追います（既定は 0）。ログは各ノードの `logs/rankR.log` |
| `launcher [stop\|status]` | コントロールパネルのランチャーを起動、停止、または状態表示 |
| `-d KIND`（コマンドの前） | この起動の drafter（`mtp`、`dflash2`、`none`） |
| `pull` | `RUNTIME=docker` のとき、各ノードで `docker pull IMAGE` |
| `-c FILE`（コマンドの前） | 別の設定ファイル |

`tf-glm53` は `sudo` を使わず、システムの設定を変えません。ランクの起動と停止はこれだけで行う前提です: 一部のランクが消えたときに全ランクを止める監視プロセスを残します（相手を失ったランクは、そうしないと永久に待ち続けます）。

## 7. API

| パス | メソッド | 説明 |
|---|---|---|
| `/v1/chat/completions` | POST | OpenAI chat: ストリーミング（`stream`、`stream_options.include_usage`）、ツール（`tools`、`tool_choice` は `auto` または `none`） |
| `/v1/completions` | POST | プロンプトのテキスト補完（chat template は付けません） |
| `/v1/models` | GET | 提供しているモデル名 |
| `/v1/tokenize`、`/v1/detokenize` | POST | トークン数と ID。プロンプト、または chat template で展開したメッセージについて |
| `/health` | GET | 状態、メモリ、稼働中の速さ、会話のプール、トークンとドラフトのカウンタ |
| `/metrics` | GET | 同じカウンタを Prometheus のテキストで |
| `/v1/experts/...`、`/v1/memory` | GET / POST | expert の使用状況、ビット、入れ替え。コントロールパネルが使います |

- 応答の `message.reasoning_content` にモデルの推論、`message.content` に答えが入ります。`max_tokens` は両方を数えます。`chat_template_kwargs` は `{"enable_thinking": false}`（推論なし）と `reasoning_effort` を受け付けます。
- 400 で断るもの: 1 以外の `n`、`logprobs`、`response_format` の `json_object`、`tool_choice` の `required`、画像（テキストのみ）、文脈を超える `max_tokens`。収まらないストリーミングのリクエストはエラーイベントで終わります。
- 接続を切ったクライアントのリクエストは取り消されます。
- キー: `API_KEY_FILE` を設定すると、クライアントは `Authorization: Bearer KEY` を送ります。キーなしでループバック以外の `HOST` にすると、API は届く人なら誰でも使えます。サーバーは平文の HTTP なので、前段に TLS を置くか閉じたネットワーク内に留めない限り、キーと文章は平文でネットワークを流れます。
- カウンタからの速さ: decode の tokens/s = Δ`completion_tokens_total` / Δ`decode_seconds_total`、prefill の tokens/s = Δ`prefill_tokens_total` / Δ`prefill_seconds_total`、ドラフトのラウンドあたりに進んだトークン = Δ`completion_tokens_total` / Δ`rounds_total`（1 ならドラフトは 1 つも残っていない）、キャッシュのヒット率 = Δ`cached_tokens_total` / Δ`prompt_tokens_total`。カウンタは実行中のリクエストの分も含み、後戻りしません。

コントロールパネルのランチャーは `/v1/launch/` の下に独自の API（status、plan、start、stop、usage、resort、check、config、nodes、保存した割り当ての allocs、alloc、allocs/save、allocs/rename、allocs/delete）を持ちます。ページが使うもので、項目はリリースの間で変わることがあります。

## 8. Expert Atlas（コントロールパネル）

- **バンク**: routed expert を 1 つの幅（2、3、4、5 ビット）で持つもの。別にダウンロードし、それぞれ manifest を持ちます。ページは全ノードがそろえている幅だけを出します。
- **計画（割り当て）**: 19,200 個の expert それぞれの幅。起動画面は前回の稼働の割合の新しい計画で開きます（稼働が 1 つも無いときはすべて 3 ビット）。割合は幅ごとに入力するか、曲線上でつまみを動かして決めます。「開く」で前回の稼働の割り当てか保存した割り当てをビット単位でそのまま戻し、そこからの起動はそのビットと保存時のバンクを使います。起動前に、各ノードのメモリと判定（収まる / ぎりぎり / 入らない）を示します。
- **利用記録**: エンジンは、プロンプトの各行（prefill）と生成した各トークン（decode）が選ぶ expert を数えます。保存した割り当ては、それぞれ保存元の稼働の利用記録を持ちます。全稼働の共通の記録はありません。新しい計画 → 稼働 → 保存なら、その稼働の記録だけ。開いた割り当て → 稼働 → 保存なら、その記録にその稼働の分を足したもの。計画は元になった割り当ての記録で expert を並べます（記録の無い計画は、ページに同梱した 12 種類の作業で測った回数で）。よく使われる expert ほど広いビットになります。
- **保存**: 自動では何も保存しません。停止時の「保存して停止」は、読み込んでいるビットと利用記録に名前を付けて保存します（既定は稼働の元になった割り当てで、上書きします。前の版は `ATLAS_DIR/allocs/trash/` へ移ります）。稼働中の「保存」も、いつでも同じことをします。割り当ては `ATLAS_DIR/allocs/user/<名前>.json` のファイルで、「開く」が一覧を出し、名前の変更と削除もできます。
- **利用記録（並べる基準）**: decode、prefill、または両方。両方は、層の中での expert の decode の選択の割合を 0.7、prefill の選択の割合を 0.3 で重みづけします。prefill と decode は別の expert を選びます（層ごとの上位 64 個の重なりは 42 %。でたらめに選べば 25 %。深い層ほど重なりが少ない）。
- **エキスパート最適化（並べ替え）**: エンジンの稼働中だけ使えます。稼働の利用記録（稼働が始めに持っていた記録 + この稼働の選択）で、読み込み済みの expert の幅を付け直します。幅ごとの expert の個数はそのままなので、メモリは変わりません。実行中や待機中のリクエストが無くなってから始め、全ランクで層をその場で入れ替え、保持している会話を捨て（古い expert で計算した KV のため）、また応答を始めます。その間に届いたリクエストは待ちます（75 層全部の変更は 4 台で 83〜90 秒でした）。結果は自動では保存しません。起動は渡された幅を読むだけで、並べ替えはしません。`EXTRA_ENV` に `TF_GLM53_MULTI` があると稼働中は何も変えず、見積もりの幅に名前（`opt-<時刻>`）を付けて保存するので、停止してそれで起動します。
- **並べ替えの効果**（4 台、半分 3 ビット / 半分 4 ビット、両方）: すべて 4 ビットのモデルからの KL ダイバージェンスが、応答のトークン（decode）で 8,192 トークンのとき 24 %、128K と 256K トークンのとき 32〜34 %、プロンプトのトークン（prefill）で 15〜22 % 減りました（`ATLAS-TESTS.ja.md`）。並べ替えに使った記録に無い種類の作業では、効果は小さくなります（約 3 分の 2）。
- **メモリ、4 台**（4 ビット KV、`STORE` 100,000、MTP）: すべて 3 ビットで文脈 737,280 トークンが収まり、半分 3 / 半分 4 ビットで 737,280、4 分の 1 が 3 / 4 分の 3 が 4 ビットで 622,592、すべて 4 ビットで 327,680、すべて 5 ビットは入りません。DFlash2 では 1 台あたり約 4 GiB 多く要ります。同じメモリでは、2 ビットの expert を混ぜた配分は参照から 13〜30 % 遠くなりました。

## 9. できること（実測）

- **速さ**（GPU クロックを 2.1 GHz に制限、リクエストは 1 件、まだキャッシュにないコーディング用のプロンプト、reasoning effort low）:

| ノード数 | プロンプト | MTP: 最初のトークンまでの時間 / decode | DFlash2: 最初のトークンまでの時間 / decode |
|---|---|---|---|
| 8 | 128K | 82.8 s / 47.5 tokens/s | 85.2 s / 53.2 |
| 8 | 256K | 172.9 s / 45.7 | 177.6 s / 52.6 |
| 8 | 512K | 376.5 s / 42.8 | 386.0 s / 47.1 |
| 4 | 128K | 120.1 s / 35.3 | 121.9 s / 42.9 |
| 4 | 256K | 253.3 s / 33.2 | 256.9 s / 40.7 |
| 4 | 512K | 565.4 s / 32.2 | 571.5 s / 37.8 |

- **キャッシュにあるプロンプト**: もう一度送った会話はプールから再開します。4 台で、703,916 トークンの会話の最初のトークンが 3 秒以内に出ました。
- **精度**（公式の BF16 モデルを公式実装で FP32 計算したものからの KL ダイバージェンス）: 8 台で 2,048 トークンの文章で約 0.013（最も確率の高いトークンの一致は約 96 %）、8,192 トークンの文章で 0.012〜0.019。4 台では同じ文章で 0.019〜0.032。routed expert をすべて 1 つの幅にしたとき（位置 6,144〜8,190）: 2 ビット 0.0517、3 ビット 0.0203、4 ビット 0.0127、5 ビット 0.0114。
- **ツールとストリーミング**: OpenAI 形式の関数呼び出しと、推論の差分つきのストリーミング応答。

## 10. できないこと

- GB10 システム 4 台または 8 台以外で動かすこと（他の GPU、他のランク数、1 台での動作には対応しません）。
- 既定でリクエストを並列に処理すること: 同時に実行するのは 1 件で、32 件まで待ち（チャットのタイトル作成と `"priority": "background"` のリクエストは最後）、それを超えると 503「the engine is busy; retry shortly」で断ります。サブエージェントを並列に動かすエージェントは、サブエージェントを別のモデルに向けた方がうまくいきます。`EXTRA_ENV` の `TF_GLM53_MULTI=4` を使うと最大 4 つの会話を保ったまままとめて decode します。`CACHE=pool`、`DCP=2`、DFlash2 または drafter なしが必要で（MTP はまとめられません）、ノードのメモリを使い、既定では無効です。
- リクエストの実行中に expert の幅を変えること（並べ替えはリクエストの終わりを待ちます）、起動後に KV キャッシュを増やすこと（起動時に確保します）。
- 画像、1 より大きい `n`、`logprobs`、JSON モード、ツール呼び出しの強制（`tool_choice` の `required`）を受け付けること。
- 提供している設定で、temperature 0 の応答が実行ごとにビット単位で同じになると約束すること: いくつかのカーネルの足し合わせの順序が変わります（精度の測定には、採点用に作った決定的な設定を使っています）。
- DFlash2 を同梱すること: 独自のライセンス（CC BY-NC-ND 4.0、非商用、研究と評価用）のもとで別にダウンロードします。使い方がそのライセンスの範囲かどうかは、運用する人が判断します。

## 11. 不具合の切り分け

| 症状 | 考えられる原因 | 対処 |
|---|---|---|
| `check` が `NG: files` / `weights` を出す | あるノードでディレクトリかチェックポイントが違う | `./tf-glm53 deploy`、`./tf-glm53 verify` |
| `NG: NCCL(...)`、`cuBLAS-13`、`libibverbs` | そのノードにライブラリが無い | 入れる（`RUNTIME.ja.md`「問題が起きたとき」） |
| `NG: RoCE-v2-GID` または RDMA デバイス | ポートに IPv4 の RoCE v2 のエントリが無い、または `IB_HCA` が違う | ポートにアドレスを付けるか `GID_INDEX` を設定。`rdma link`、`ibdev2netdev` |
| `NG: GPU-busy` | 別のプロセスが GPU を使っている | それを止める（`nvidia-smi`） |
| `NG: memory(N<M GiB)` | 空きメモリが足りない | ノードのメモリを空けるか `STORE` を下げる |
| あるノードで全項目が `NG` | 1 台目からそのノードに ssh が通らない | `ssh -o BatchMode=yes ADDRESS true` が通ること |
| `up`: `a rank stopped` と `NCCL WARN` | ネットワークの名前かアドレスの誤り、ポートが塞がれている | `NODES` は RoCE ネットワークのアドレスに。`SOCKET_IFNAME`、`IB_HCA` を全ノードで正しく |
| `up`: `cannot listen on` | そのノードで `PORT` が使われている | 空けるか `PORT` を変える |
| `up`: `the smoke test failed` | 応答が質問に答えなかった | 失敗した質問が受け取った応答を示し、ランク 0 のログにリクエストが出ます |
| `up`: `not ready after N s` | ディスクやネットワークストレージが遅い | `READY_TIMEOUT` を上げる。`MASTER_PORT` が空いているか確かめる |
| `PoolValuesDiffer` | ランクが違う設定で起動された | すべてのランクを 1 つの `glm53.conf` から `tf-glm53` で起動 |
| サーバーが答えなくなり、全ランクはまだ動いている | 固まった | `./tf-glm53 down`、`./tf-glm53 up` |
| ノードのメモリが尽きた | 文脈か STORE が大きすぎる | 各ランクは `oom_score_adj` 1000 で動くので、カーネルがそのランクを止め、監視が残りを止め、ノードは動き続けます。`STORE`/`CONTEXT` を下げる |
| パネル: ある幅が「データなし」 | どこかのノードにそのバンクが無い | そこにダウンロードし、`./tf-glm53 verify-banks N` |
| `slot cache: WARNING: no store`（`CACHE=slots`） | 起動時にあるランクで `STORE` 分のメモリが足りなかった | メモリを空けるか `STORE` を下げ、`down` と `up` |
| ログに `PoolWriteRefused` | あるランクが、リクエスト自身のブロック以外へのプールの書き込みを拒んだ | そのリクエストの終わりで全ランクが止まります。`./tf-glm53 up` |

ログ: 各ノードの `logs/rankR.log`（前回の起動の分は `.prev`）、`logs/watch.log`（監視が消えていたと判断したランク）、ランチャーのログは `logs/` に。

## 12. 間違えやすい点

- `max_tokens` は推論のトークンも数えます。`max_tokens` が小さいと、応答が推論の途中で終わることがあります。
- エンジンの起動時の行は、drafter にかかわらず `drafts: on` と表示します。使っている drafter は `tf-glm53 status` が示します。
- 「4 台」は、`./tf-glm53 up` では 4 台用のチェックポイントと `KV=fp4` が必要です。コントロールパネルでは、どちらのチェックポイントでもバンクと一緒に使えます。
- 並べ替えの測定は、BF16 モデルではなく、すべて 4 ビットのモデルに対するものです。`ATLAS-TESTS.ja.md` にどちらかを書いています。
- chat template の user のターンの中では、モデルは利用者自身の文章をうまく予測しません。これはプロンプトに対する KL ダイバージェンスのように利用者の文章を予測するときの話で、応答の話ではありません。`ATLAS-TESTS.ja.md` の測定は、プロンプトのトークンを template の冒頭を除いて採点しています（「測り方」）。
- プールの会話のキャッシュには 512 以上の `STORE` が必要です。
- コンテナには GPU、`/dev/infiniband`、ホストネットワーク、`--ulimit memlock=-1 --ulimit nofile=1048576:1048576` が必要です。コンテナの中では、`tf-glm53 check` は他のコンテナの GPU プロセスを見られません。
- API は既定でループバックで待ち受けます。他のマシンに提供するには `HOST` が必要で、そのとき `API_KEY_FILE` が無ければ API は誰でも使える状態になります。
