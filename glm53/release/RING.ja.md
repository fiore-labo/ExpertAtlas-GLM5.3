# スイッチなし、4 台の DGX Spark をリングで

4 台構成 (`T4.ja.md`) は、スイッチを使わず 200 Gb/s の直結でリング状につないだ 4 台の NVIDIA DGX Spark でも
動きます。エンジン、チェックポイント、bank、コントロールパネルは同じで、変わるのはランクどうしの届け方だけです。
TensorFold 1.0.2 から Fiore-lab が作った非公式の派生版で、TensorFold プロジェクトのリリースではありません。

## 動き方

- 各ノードは両隣へ直接届きます。向かいのノード (線 2 本先) には自分の線がなく、そこへ行くものは隣が中継します。
  - prompt の all-to-all は、向かいのノード分のブロックを半分ずつ、両隣を経由して送ります。
  - RoCE の decode の集団通信 (`TF_GLM53_ROCE=1`) は、向かいのノードの分を、それを持つ隣が同じ slot へ転送します。
    GPU のカーネルは変わりません。
- NCCL はリングだけをつなぎ (`NCCL_ALGO=Ring`)、向かいのノードにはつなぎません。各ノードの PCIe の半分 4 つを
  使います (4 チャネル)。
- ランクはリング上のノードの位置です。decode の context 並列のグループ (DCP 2) は、どれも線でつながった組です。
- prompt の部分和はリングで足し合わせます (`PREFILL_REDUCE=ring`。reduce-scatter は断ります)。複数の会話の
  取り分による reduce (AR2) はリングでは使いませんが、`MULTI` はリングでも 4 会話まで動きます。
- NCCL は 2.30.7 に NVIDIA/nccl#2393 の AArch64 の送信 fence (commit `05d026f4`) を入れて sm_121 向けにビルドした
  ものです。`RUNTIME=docker` では、リリースのイメージの `/opt/nccl-fenced` にあり、`tf-glm53 check` が確かめます。
  `RUNTIME=host` では全ノードの同じパスに置き、ランチャーが SHA-256 を確かめます。ビルドの手順は下の「fence 入りの NCCL」にあります。

## 配線と番地

- 各ノードのポート 0 を、リングの次のノードのポート 1 につなぎます。ポート 0 どうし・ポート 1 どうしでつなぐと、
  NCCL の subnet-aware routing が一部の線でデバイスを見つけられず (待ち受け側は自分のデバイスの番地だけを知らせる)、
  接続に失敗します。
- 線ごと・PCIe の半分ごとに /24 を 1 つ割り当て (ConnectX-7 の 1 ポートは `rocep1s0f*` と `roceP2p1s0f*` の
  半分 2 つ)、MTU は 9000 にします。`arp_ignore=1`、`arp_announce=2`、`rp_filter=2` は DGX OS に入っているので、手で設定する必要はありません。
  ここで使った例 (リングの順は node-0、1、3、2):

| 線 | 半分 0 | 半分 1 |
|---|---|---|
| node-0 – node-1 | 172.16.88.0/24 | 172.16.89.0/24 |
| node-3 – node-2 | 172.16.90.0/24 | 172.16.91.0/24 |
| node-0 – node-2 | 172.16.92.0/24 | 172.16.93.0/24 |
| node-1 – node-3 | 172.16.94.0/24 | 172.16.95.0/24 |

node-0 のアドレスです。ポート 0 は node-1 に、ポート 1 は node-2 につないであります。`enp1s0f*` が半分 0、`enP2p1s0f*` が半分 1 で、最後の数字はノードごとに変えます:

```sh
sudo tee /etc/netplan/01-cx7.yaml >/dev/null <<'EOF'
network:
  version: 2
  renderer: NetworkManager
  ethernets:
    enp1s0f0np0:
      mtu: 9000
      addresses: [172.16.88.10/24]
    enP2p1s0f0np0:
      mtu: 9000
      addresses: [172.16.89.10/24]
    enp1s0f1np1:
      mtu: 9000
      addresses: [172.16.92.10/24]
    enP2p1s0f1np1:
      mtu: 9000
      addresses: [172.16.93.10/24]
EOF
sudo chmod 600 /etc/netplan/01-cx7.yaml
sudo netplan apply
ip -br addr    # 半分 4 つが UP で、アドレスが付いている
rdma link      # 半分 4 つが ACTIVE
```

- 配線のあとは、全部の線を両方の向きで `ib_write_bw` で確かめます。ここでは 1 本の流れで半分あたり 98 Gb/s、
  4 本の線の両方の向きを同時に流して半分あたり 48〜49 Gb/s、各ノードが約 194 Gb/s 送りながら 194 Gb/s 受けました。
  動いている間に抜き差ししたポートは 5〜13 Gb/s のままで、ノードを再起動すると戻りました。
- 待ち合わせと ssh は管理ネットワーク (`SOCKET_IFNAME`) を通るので、向かいのノードどうしに線は要りません。ssh の手順は `QUICKSTART.ja.md` の 1 章にあります。リングでは管理ネットワークのアドレスを使います。
- `docker run ... IMAGE up` とコントロールパネルのノード確認は、LLDP で線をたどるので、全ノードに `lldpd` が要ります。DGX OS の更新で入ります。`lldpctl` でノードの隣が見え、無いときは `sudo apt install lldpd` で入れます。

## fence 入りの NCCL

Arm では、2 つの読み込みの順番が保証されていないので、NCCL の通信スレッドが CTS の枠から古い数を読むことがあります。すると、エラーなしで待ち続けるか、書き込みが足りなくなります。
修正は acquire fence を 1 つ足すものです (NVIDIA/nccl#2393、commit `05d026f4`)。NCCL の開発ブランチにあり、2.32.3 までのリリースには入っていないので、NVIDIA の wheel にはありません。NCCL の開発者は、GB10 4 台とスイッチで報告された無言の停止 (NVIDIA/nccl#2334) もこれで直ると見ていますが、その報告で直ったことはまだ確かめられていません。

リリースのイメージにはこのビルドが入っていて、スイッチでもリングでもこれを読むので、イメージを使うなら何もすることはありません。`RUNTIME=host` では、リングには必須で、wheel でも動くスイッチには推奨です。ビルドの手順 (CUDA 13 のあるノードで 2 分ほど):

```sh
git clone https://github.com/NVIDIA/nccl && cd nccl
git checkout v2.30.7-1
git cherry-pick 05d026f4
make -j8 src.build NVCC_GENCODE="-gencode=arch=compute_121,code=sm_121"
sha256sum build/lib/libnccl.so.2.30.7
```

`build/lib/libnccl.so*` を全ノードの同じパスに写します。ここで使ったビルドの sha256 は
`f75ac06821bbf42793a4951d6fc89061526a3fa1ad37b565c4146b0995a53299` で、`docker/Dockerfile` が受け付けるのはこのファイルだけです。イメージのビルドにはこれが要ります (`--build-context fenced=DIR`)。`DIR` には `build/lib/libnccl.so.2.30.7` と、ソースの `LICENSE.txt`、`ThirdPartyNotices.txt` を置きます。どれかが欠けるとビルドは失敗します。
`RUNTIME=host` なら `NCCL_LIB` に自分のビルドを指定し、リングでは `NCCL_SHA256` も指定します。sha256 はツールチェーンによって変わることがあります。

## 設定

`docker run ... IMAGE up` とコントロールパネルのノード確認は、リングを自分で見つけて `TOPOLOGY`、`NODES`、
`SOCKET_IFNAME`、`IB_HCA` を `glm53.nodes.conf` に書きます。手で設定するときは、`glm53.t4.conf.example` の 4 台の設定に加えて:

```sh
TOPOLOGY=ring4
NODES=(172.16.10.200 172.16.10.201 172.16.10.203 172.16.10.202)   # 管理ネットワークの番地、リングの順
SOCKET_IFNAME=enP7s7                                                  # 管理ネットワーク
IB_HCA=rocep1s0f0,roceP2p1s0f0,rocep1s0f1,roceP2p1s0f1                # RDMA デバイス 4 つ
RING_CHANNELS=4
NCCL_LIB=$HOME/nccl-fenced/libnccl.so.2.30.7                          # fence 入りの NCCL
NCCL_SHA256=<その sha256>
```

`./tf-glm53 check` がリングを確かめます: ノードがリングの順に並ぶこと、線ごとにサブネットが 2 つあること、向かいの
ノードとサブネットを共有しないこと、どのデバイスにも IPv4 の RoCE v2 の番地があること。向かいのノードへ直接届く
設定は断ります。

`ring4` の代わりに `TOPOLOGY=auto` と書くと、`check` と起動のたびにつなぎ方を判定します（判定は
`./tf-glm53 topology`、`--json` で見られます）。4 台がリングにつながっていれば `ring4` で、NODES をリングの順に
並べ替え（ランク 0 はそのまま）、`IB_HCA` に RDMA デバイス 4 つ、`SOCKET_IFNAME` にランク 0 の番地を持つ
インターフェースを使います。この 2 つは書かなくてかまいません。同じ設定でスイッチにつながっていれば `full` です。
どちらでもないつなぎ方（線が抜けている、片側の半分が落ちている、1 台の 2 本が逆のポート、向かいどうしが同じ /24）は、
直すところを示して断ります。黙って別の形に切り替えることはしません。

## 速さ

リングを立ち上げたときに、リリース r3-102 のエンジンで測りました。リングの 4 台、routed expert は半分 3 bit・半分 4 bit
(パネルの計画、9,600 個ずつ)、`T4.ja.md` の設定、MTP のドラフター、4 bit の KV キャッシュ。キャッシュの効かないコーディングの prompt を 1 件ずつ (推論の effort は low、
返答は最大 4,000 トークン)、ウォームアップの後に 1 回。GPU のクロックは制限なし (2,080〜2,405 MHz を観測)。
スイッチの 4 台構成は `T4.ja.md` から (GPU のクロック上限 2.1 GHz、2 回の中央値):

速度は環境によって違います（チェックポイント、プロンプト、クロックなど）。数値は目安です。

| prompt | リング: 最初のトークンまで (秒) | リング: decode (トークン/秒) | スイッチ: 最初のトークンまで (秒) | スイッチ: decode (トークン/秒) |
|---|---|---|---|---|
| 129,441 トークン (128K) | 125.4 | 35.9 | 120.1 | 35.3 |
| 260,230 トークン (256K) | 264.8 | 34.6 | 253.3 | 33.2 |
| 395,322 トークン (384K) | 421.9 | 33.0 | - | - |

- リングは最初のトークンが 4〜5 % 遅く、decode は同じか少し速い。
- この起動では context length が 573,440 位置になりました: パネルにリングでの起動の実測がなく、余裕を取ったため。384K の prompt
  の間も各ノードに 6〜7 GiB の空きがありました。

## 精度

公式の BF16 モデルからの KL ダイバージェンス。基準の 8,192 トークンの窓 4 つで、位置の範囲ごと (a: prompt 1,024 行の
後に decode の窓、b: prompt 6,144 行の後に decode の窓)。決定的な構成、8 bit の KV キャッシュ。リングでは prompt の
部分和をリングで足し合わせ、スイッチの測定は reduce-scatter でした。

| 位置 | リング: 半分 3・半分 4 bit | リング: 全部 3 bit | スイッチ: 半分 3・半分 4 bit | スイッチ: 全部 3 bit | スイッチ: 全部 4 bit |
|---|---|---|---|---|---|
| a 1,024〜2,047 | 0.0154 | 0.0206 | 0.0156 | 0.0204 | 0.0120 |
| a 2,048〜4,095 | 0.0236 | 0.0347 | 0.0258 | 0.0346 | 0.0208 |
| a 4,096〜6,143 | 0.0250 | 0.0324 | 0.0259 | 0.0321 | 0.0198 |
| a 6,144〜8,190 | 0.0166 | 0.0211 | 0.0160 | 0.0209 | 0.0132 |
| b 6,144〜8,190 | 0.0158 | 0.0199 | 0.0171 | 0.0203 | 0.0127 |

- 同じ全部 3 bit の重みで、リングとスイッチの差はどの範囲も 0.0001〜0.0004 で 2 % 未満 (top-1 の一致はリング
  93.8〜95.4 %、スイッチ 93.6〜95.5 %): 中継と、prompt の部分和のリングでの足し合わせは精度を変えていません。
- 半分ずつの 2 列は、3 bit にした expert が同じではありません: スイッチの列は 4 台用チェックポイントの混在
  (`T4.ja.md`)、リングの列はパネルが使用回数から作った計画です。

## まだ試していないこと

- 障害: 動いている間にノード、線、中継を止めたとき。
- 負荷をかけた長時間 (数時間) の運転。
- `TOPOLOGY=auto` での起動（判定と `check` はリングでもスイッチでも通ります）。
