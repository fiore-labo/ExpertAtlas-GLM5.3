Expert Atlas の機能を 1 つずつ説明します。何をするか、なぜあるか、どう使うかの 3 つです。画面は `SCREENS.ja.md`、操作の細かい決まりは
`PANEL-GUIDE.ja.md`、設定の全項目は `CONFIG.ja.md` にあります。

下の実測値は、横に書いたリリースの文書からの引用で、条件もその文書のとおりです。速さやメモリは、ノード・prompt・設定で変わります。目安として見てください。

## 1. リングとスイッチ、ノード確認

**何をするか。** Expert Atlas は、1 つの RoCE v2 スイッチにつないだ DGX Spark 4 台か 8 台で動きます。スイッチなしで 4 台をリングにつないでも動きます。
ノード確認は、どちらのつなぎ方かを調べ、全ノードを確かめて登録します。

**なぜあるか。** リングならスイッチは要りません。各ノードの ConnectX-7 の 2 つのポートを、両隣のノードに直接つなぎます。エンジン、重み、パネルは
どちらでも同じです。リングでは向かいのノードへの直接の線がないので、両隣が中継します。4 台での実測 (`RING.ja.md`) では、最初のトークンはスイッチより
4〜5% 遅く、decode は同じか少し速く、精度は同じでした。

**使い方。**

- ノードが登録されていない間、パネルはノード確認で開きます。ボタンを 1 回押すと、配線を調べ、全ノードで `tf-glm53 check` を実行し
  (ssh、GPU、メモリ、待ち合わせ、RDMA、NCCL、ファイル)、無いノードにはパッケージを配り、ノードを `glm53.nodes.conf` に書きます。
- **リング**: head が LLDP で配線をたどるので、全ノードに `lldpd` が要ります。各ノードのポート 0 を、次のノードのポート 1 につなぎます。
  リングでは、レーンごとの帯域も測ります。
- **スイッチ**: head が ConnectX-7 の /24 に ssh を試し、答えたノードを並べます。台数を選び、使うノードにチェックを入れます。
  他の人のノードもあるスイッチでは、先に選んでから押してください。
- `docker run ... IMAGE up` も、コマンドラインで同じ確認をします (`QUICKSTART.ja.md`)。
- `glm53.nodes.conf` には `TOPOLOGY`、`NODES`、`SOCKET_IFNAME`、`IB_HCA` が入ります。`glm53.conf` より優先されます。

## 2. 2・3・4・5 bit の expert

**何をするか。** モデルには routed expert が 19,200 個あります (層 3〜77、1 層に 256 個)。どれも 2・3・4・5 bit のどれかで読み込めます。
幅ごとに bank (ディレクトリ) が 1 つあり、全ノードで同じパスに置きます。

**なぜあるか。** 広い幅ほど公式のモデルに近くなりますが、メモリを多く使い、context と KV キャッシュに回せる量が減ります。
どこで釣り合わせるかを、使い方に合わせて選べます。

| 幅 | bank の大きさ | KL ダイバージェンス (全 expert をその幅に。`AI-GUIDE.ja.md`) |
|---|---|---|
| 2 bit | 187.3 GB | 0.0517 |
| 3 bit | 277.9 GB | 0.0203 |
| 4 bit | 368.5 GB | 0.0127 |
| 5 bit | 459.1 GB | 0.0114 |

(公式の BF16 モデルとの KL ダイバージェンス。位置 6,144〜8,190。小さいほど近い。)

4 台では (`T4.ja.md`。4 bit の KV キャッシュ、context length は最大 737,280 を求めた計画): 全部 3 bit と、半分 3 bit・半分 4 bit は、どちらも求めた
737,280 が入りました。全部 4 bit は 327,680、全部 5 bit は入りませんでした。同じメモリでは、2 bit を混ぜた組み合わせは、混ぜない組み合わせより
参照から 13〜30% 離れました。ほかを 3 bit に下げて 5 bit を足しても、測れるほどの差はありませんでした。

**使い方。**

- Base の重みと 3 bit の bank は必ず要ります。2・4・5 bit の bank は任意です。bank の無い幅は選べません。
- ディレクトリは起動設定の [ WEIGHTS ] か、`BANK_2`〜`BANK_5` で指定します (`QUICKSTART.ja.md`)。
- `docker run` の行に `-e BITS=N` を付けると、全 expert を 1 つの幅で起動します。パネルでは expert ごとに幅を変えられます (次の章)。

## 3. bit の割り当て

**何をするか。** 起動設定の [ BIT ALLOC ] で、幅ごとに expert の割合を決めます。よく使われる expert ほど広い bit になります。

**なぜあるか。** よく選ばれる expert と、あまり選ばれない expert があります。よく使う expert に bit を回すと、同じメモリで、実際に選ばれる expert の
平均 bit が上がります。

**使い方。**

- 5・4・3 bit の割合を入れます。残りはデータのある一番狭い幅になるので、合計はいつも 100% です。
- expert は利用記録 (それぞれが選ばれた回数) の順に並びます。並べるときは、decode の割合を 0.7、prefill の割合を 0.3 で重みづけします。
  返答の文章を最もよく保った重みです (`ATLAS-TESTS.ja.md`)。
- 自分の利用記録のない計画は、ページに入っている回数で並べます。このリリースのために測った 12 分野の回数です (コーディング、エージェント、
  日本語と英語の文章、Linux の運用、セキュリティ)。
- 利用記録のボタン (decode、prefill、両方) は表示だけを変えます。計画の bit は変わりません。
- ノードごとのメモリと判定 (起動できます、メモリ不足) は、入力に合わせて変わります。

## 4. 割り当ての保存と読み込み

**何をするか。** 割り当ては、全 expert の bit と利用記録の組です。名前を付けて保存し、あとで開けます。

**なぜあるか。** 自分の使い方に合った計画や、エキスパート最適化の結果を、次の起動でも使えます。利用記録も一緒に動くので、次の稼働の分が足されていきます。

**使い方。**

- 自動では保存しません。
- 稼働パネルの [ BIT ALLOC ] の **保存** で、いつでも保存できます。**保存して停止** は、止めるときに保存します。
- 起動設定の **開く** に、前回の稼働の割り当てと保存した割り当てが並びます。開いた割り当ては bit そのままで計画になり、起動はそれを使います。
- 保存したものは **名前の変更** と **削除** ができます。削除したものや上書きした前の版は、ランチャーのごみ箱に移ります。
- ファイルは head の、リリースのディレクトリの `atlas/allocs/user/<名前>.json` にあります (`CONFIG.ja.md` の `ATLAS_DIR`)。
- コマンドラインでは、`docker run` の行に `-e ALLOC=名前` を付けます。前回の起動の計画で起動するなら `./tf-glm53 start` です (`QUICKSTART.ja.md` の 6 章)。

## 5. エキスパート最適化

**何をするか。** エンジンの動作中に、載っている expert を、この稼働の利用記録 (起動したときの記録 + この稼働の選択) で並べ替えます。
幅ごとの個数はそのままなので、メモリは変わりません。

**なぜあるか。** 同梱の回数は一般的な見込みです。実際の使い方では、選ばれる expert が違います。並べ替えると、自分がよく使う expert が広い bit になります。
4 台、半分 3 bit・半分 4 bit での実測 (`AI-GUIDE.ja.md`、`ATLAS-TESTS.ja.md`): 全部 4 bit のモデルとの KL ダイバージェンスは、返答のトークンで
8,192 トークンのとき 24%、128K と 256K で 32〜34% 下がりました。回数に入っていない種類の仕事では、効果は小さめ (約 3 分の 2) でした。

**使い方。**

- [ BIT ALLOC ] の **エキスパート最適化** を押します。見積もりに、変わる expert の数、推論が止まるおよその時間、各ノードに入れ替えのメモリがあるかが出ます。
- **実行** を押します。推論中と待ちの要求がなくなってから始まります。その間に来た要求は待ちます。
- 75 層を全部入れ替えると、4 台で 83〜90 秒かかりました。
- KV pool に残した会話は消えます。その KV は前の expert で計算したものだからです。
- 各ノードに、最も大きい層の新しい写しの分と 2 GiB の空きが要ります。足りないノードがあると、パネルはそのノードの名前を出して断ります。
- 結果は自動では保存しません。**保存** を押してください。起動は渡された幅を読むだけで、並べ替えはしません。
- 同時推論のときも同じように動きます。

## 6. Context length、KV サイズ、KV pool

**何をするか。** KV キャッシュは、すべての会話が分け合う 1 つのプールです。前の会話がそこに残るので、次のターンで prompt を計算し直さずに済みます。

- **Context length** (`CONTEXT_LENGTH`): 1 回の要求の最長で、prompt と返答の合計です。最大 1,048,576 です。
- **KV サイズ** (`KV_SIZE`): プール全体が持つトークン数です。context length + 512 以上です。残りに前の会話が入ります。

**なぜあるか。** エージェントやチャットは、同じ長い頭を何度も送ります。長い prompt の計算には分単位の時間がかかります (4 台で 128K トークンに約 120 秒、
`T4.ja.md`)。キャッシュから読めば、ほとんどかかりません。4 台での実測 (`T4.ja.md`): 703,916 トークンの会話をもう一度送ると、703,899 位置を
プールから再開し、最初のトークンまで 3 秒未満でした。

**しくみ** (`RUNTIME.ja.md`)。

- プールは 256 位置のブロックでできています。要求は、どの会話からでも、キャッシュにある一番長い同じ頭から再開します。
- 同じように始まる会話 (同じ system prompt やサブエージェント) は、共通のブロックを 1 つだけ持ちます。
- 会話は 64 まで残ります。プールがいっぱいになると、最も長く使われていない会話から、末尾のブロックを返します。
- ブロックは使う前に要求のトークンと照合します。少しでも疑わしければ、その要求は最初から計算します (コールド)。
- エキスパート最適化と再起動で、会話は消えます。
- Byte Resume (`TF_GLM53_BYTE_RESUME`、既定はオン) は、モデルがトークナイザーと違う切り方をした文章でもキャッシュを保ちます。何もする必要はありません。

**使い方。**

- 起動設定の [ NODE ] で、context length、KV サイズ、KV の形式を決めます。既定では、計画が残す空きを全部 KV に使います。
- **KV の形式**: FP4 は FP8 より 1 位置あたりのメモリが少なく (10 万位置で 1.73 GiB と 2.55 GiB。`RUNTIME.ja.md`)、精度は少し下がります
  (KL ダイバージェンスが 0.003〜0.005 増えました。`T4.ja.md`)。
- **OS に残す** (`RESERVE_GB`): 多く残すほど、KV に回せる量が減ります。
- 稼働パネルの KV POOL に、使っている割合、残している会話、prompt のうちキャッシュから読んだ割合が出ます (`SCREENS.ja.md`)。

## 7. 同時推論と GPU の配分

**何をするか。** 既定では、エンジンは要求を 1 本ずつ処理します。ほかの要求は 32 本まで待ち、それを超えると混雑として断ります。
同時推論 (`MULTI`。パネルでは 1〜4) にすると、その数までの会話を同時に動かし、いっしょに decode します。

**なぜあるか。** 何人かの利用者や、サブエージェントを使うエージェントに、順番待ちでなく同時に応えられます。そのぶんノードのメモリを使います。
リングで context length 131,072、OS に残す 16 GiB のとき (`BEFORE-START.ja.md`。最初の起動の推定) は、KV が MTP の 753,664 トークンから、
DFlash2 と `MULTI=4` の 360,448 に減りました。

**使い方。**

- 起動設定の **同時推論** で 1〜4 を選びます (1 は 1 本ずつ)。`docker run` の行の `-e MULTI=N` でも指定できます。MTP、DFlash2、ドラフターなしの
  どれでも使えます。3 台ではまだ使えません。
- `MULTI_WAIT` (既定 600 秒): 要求が空きを待つ上限です。過ぎると混雑として断り、クライアントがやり直します。
- 動作中は、[ NODE ] に **同時推論** と 3 つの操作が出ます。
  - **GPU の配分**: prompt の計算と decode 中の会話が重なる間の、GPU の時間の分け方です。prefill 100% は prompt を先に計算します。
    decode 100% は返答を先に進めます。起動時の値は decode 30% です (`MULTI_DECODE_SHARE`)。
  - **優先 prompt**: 新しく計算するトークンがこの数 (既定 8,192) 以下の prompt は、長い prompt より先に入ります。数えるのはキャッシュより後ろの分だけ
    なので、長い会話の次のターンは新しい部分だけで数えます。
  - **実行中の prefill も追い越す** (既定はオフ): 実行中の長い prefill も、優先 prompt に順番を譲ります。終わったチャンクから続けます。
- 稼働パネルでの変更は、エンジンが止まるまで効きます。次の起動でも使うには、エンジン設定で決めます。

## 8. ドラフター: MTP と DFlash2

**何をするか。** ドラフターが次のトークンを下書きし、モデルがそれを確かめます。認めたトークンはまとめて出るので、decode が速くなります。
返答はいつもモデル自身のものです。

**なぜあるか。** decode を速くするためです。リリース r2-102 での実測 (`RUNTIME.ja.md`。このリリースでは測り直していません): 4 台・128K の prompt で、
decode は MTP が毎秒 35.3 トークン、DFlash2 が 42.9 でした。8 台では 47.5 と 53.2 でした。

**使い方。**

- **MTP** (既定): 重みに入っている MTP の層を使います。ダウンロードは要りません。
- **DFlash2**: 別のモデル `incoai/GLM-5.3-DFlash2` で、ライセンスも別です。同梱していません。全ノードにダウンロードし、そのディレクトリを指定します
  (`DRAFTER`、または [ WEIGHTS ] のドラフターの行)。全ノードにそろうまで、パネルでは灰色です。1 ノードあたり 4 台で約 3 GiB、8 台で約 4 GiB 多く使うので (ランチャーの見積もり)、
  KV は小さくなります。
- **なし**: ドラフターを使いません。
- 起動設定の **ドラフター** か、`-e DRAFTER_KIND=mtp|dflash2|none` で選びます。

## 9. 思考の制御 (REASONING CONTROL)

**何をするか。** GLM-5.3 は答える前に考えます。`max_tokens` には思考も入ります。[ REASONING CONTROL ] は、返答のうち思考に使える量と、
思考をいつ整理するかを決めます。

**なぜあるか。** 思考が長いと、max_tokens を使い切って答えの分が残らないことがあります。とても長い思考は KV も埋めます。
この設定で答えの分を残し、思考の KV を一定の大きさに抑えます。クライアントには思考が全部届きます。

**使い方。** 稼働パネルで変えると、その後に始まる要求から効き、`glm53.conf` にも書きます。要求自身の指定が先です。

- **思考の上限** (`THINKING_SHARE`): 各返答の max_tokens の 5%〜100% (上限なし)。上限に来ると、エンジンが改行で思考を閉じ、残りでモデルが答えます。
- **中間整理** (`THINKING_FOLD`): モデルが思考のチェックポイント (ここまでの結論、除外したこと、まだ決まっていないこと、次に調べること) を書きます。
  エンジンは context の中の思考を、そのチェックポイントに置き換えます。上限は書いたトークンの数で数えるので、context length を超えることがあります。
- **整理する間隔** (`THINKING_FOLD_SHARE`): どのくらいごとに整理するかを、max_tokens に対する割合で決めます (最低 1,024 トークン)。
  100% は上限に来たときだけ整理します。
- **思考完了時整理** (`THINKING_FOLD_AT_CLOSE_SHARE`): モデルが思考を閉じるとき、先に思考を整理します。長い推論が答えの前の計画になり、
  次のターンには整理した文章だけが渡ります。
- **残りのお知らせ** (`THINKING_NOTICE`。エンジン設定だけ。再起動が要ります): 決まったトークン数ごとに、使った思考のトークン数と残りをモデルに知らせます。
  モデルは自分でペースを配分できます。
- 思考の予算の終わり近くでは、エンジンがモデルに思考を書き直させます (`THINKING_FOLD_AT_BUDGET`、既定はオン)。そのため、返答が上限より多く書くことがあります。

エンジン設定の画面でも同じ値と、それに関わる大きさを決められます (`CONFIG.ja.md`)。

## 10. 正常性確認

**何をするか。** [ NODE ] の **正常性確認** は、動いているエンジンに約 1,000 トークンの要求を 1 本送り、答えを判定します。正しい答えは、
prompt を読まないと出せません。

**なぜあるか。** エンジンが動いているだけでなく、prompt を読んで正しく答えることを確かめるためです。

**使い方。** **正常性確認** を押します。正しければサークルの上に **推論正常** が数秒出ます。**推論異常** はボタンの下に理由と一緒に残ります。
ふつうは約 3 秒で終わります。長い推論の後ろでは順番を待ちます (最大 600 秒)。

## 11. エンジンコアと RDMA の行

**何をするか。** GB10 の CPU には、Cortex-X925 と Cortex-A725 の 2 種類のコアがあります。エンジンのスレッドをどこで動かすかを、2 つの設定で決めます。

- **RDMA 通信のコア** (`ROCE_PROXY_CORES`。既定は A725): RoCE の通信スレッドです。rank ごとに 2 本あり、decode の間は回り続けます。
  A725 にするとコア 0 と 10 で動きます。OS にするとスケジューラーに任せ、X925 で動くことがよくあります。
- **エンジンコア** (`ENGINE_CORES`。既定は OS): OS なら各 rank がすべてのコアを使います。A725 なら A725 のコアだけを使います。

**なぜあるか。** 回り続けるスレッドが速い X925 で動くと、チップが熱くなります。4 台では、通信スレッドを A725 にすると、decode の速さは同じまま、
チップの温度が 5〜16 °C 下がりました (`CONFIG.ja.md`)。エンジンを A725 だけで動かしたときの速さは、まだ測っていません。

**使い方。** どちらもエンジン設定の「ノードと並列」で決め、次の起動から効きます。動作中は [ NODE ] に結果が出ます。RDMA の列は、各ノードの
2 本の通信スレッドが動く CPU です (たとえば 0·10)。表の下の行には、RDMA 通信スレッドとエンジンコアが出ます。

## 12. 表示設定

**何をするか。** **表示設定** の引き出しで、パネルの見た目を変えます。言語、サークルの並べ方・残光・明るさ、光の色、外周の文字、数字、中心、配色です。
エンジンは変えません。

**なぜあるか。** 自分の画面で見やすくするためです。設定はブラウザでなくレーンに残るので、パネルを開く人は皆同じ見た目になります。

**使い方。**

- 設定は head の、パッケージのディレクトリの `launch/panel-settings.json` に残ります (`EXTRA_ENV` の `TF_PANEL_SETTINGS` で場所を変えられます)。
  そのレーンを開くどのブラウザでも同じパネルになります。
- ノード確認のノードの一覧とチェックも、同じファイルに残ります。
- **既定に戻す** (2 回押す) は、レーンのすべてのブラウザの表示設定を既定に戻します。言語とノードはそのままです。
- リングとスイッチのレーンは、設定で別のものを選んでいなければ、光の色を bit ごとに変え、配色 Material · 藍 で開きます。

## 13. 構造化出力

**何をするか。** 返事の答えを JSON に保ちます。JSON のオブジェクトか、送った JSON Schema に合う JSON です。エンジンは token ごとに、答えがその形から
外れない token の中からだけモデルに選ばせます。なので答えは JSON として読め、スキーマにも合います (`max_tokens` で先に切れたときを除きます)。
文法は llguidance 1.9.1 のもので、最初のノードで動きます。既定でオンです (`STRUCTURED`)。

**なぜあるか。** 返事をプログラムが読むとき (情報の抜き出し、フォーム、エージェントの 1 手など)、期待どおりのキーと型を持つ JSON をそのまま受け取れます。
モデルに聞き直す必要がありません。

**使い方。** リクエストで指定します。

- `/v1/chat/completions` (OpenAI の chat): JSON のオブジェクトなら `"response_format": {"type": "json_object"}`、スキーマに合う JSON なら
  `{"type": "json_schema", "json_schema": {"name": "...", "schema": {...}}}` です。vLLM の書き方も読みます: `"guided_json": SCHEMA`、
  `"structured_outputs"` の `{"json": SCHEMA}` か `{"json_object": true}`。`{"type": "text"}` は制約なしです。
- `/v1/responses` (OpenAI の Responses API): `"text": {"format": {"type": "json_schema", "name": "...", "schema": {...}}}`、
  または `{"type": "json_object"}`。
- `/v1/messages` (Anthropic の Messages API): `"output_config": {"format": {"type": "json_schema", "schema": {...}}}`。

chat API で、思考なしの例:

```sh
curl -s http://NODE:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "glm-5.3", "max_tokens": 300,
  "chat_template_kwargs": {"enable_thinking": false},
  "messages": [{"role": "user", "content": "A city in Japan and its prefecture."}],
  "response_format": {"type": "json_schema", "json_schema": {"name": "city", "schema": {
    "type": "object",
    "properties": {"city": {"type": "string"}, "prefecture": {"type": "string"}},
    "required": ["city", "prefecture"]}}}}'
```

Python の `openai` パッケージで、思考ありの例:

```python
import json
from openai import OpenAI

client = OpenAI(base_url="http://NODE:8000/v1", api_key="none")
r = client.chat.completions.create(
    model="glm-5.3", max_tokens=4000,
    messages=[{"role": "user", "content": "Three prime numbers above 100."}],
    response_format={"type": "json_schema", "json_schema": {"name": "primes", "schema": {
        "type": "object",
        "properties": {"primes": {"type": "array", "items": {"type": "integer"},
                                  "minItems": 3, "maxItems": 3}},
        "required": ["primes"]}}})
choice = r.choices[0]
if choice.finish_reason == "length":
    raise SystemExit("cut by max_tokens: the JSON is not finished")
print(json.loads(choice.message.content)["primes"])
```

- **思考ありのとき。** chat API と Responses API では、GLM-5.3 は既定で思考します。Messages API では `thinking` で頼んだときです。思考は自由に書き、
  制約は思考が閉じたところから始まります。思考は `reasoning_content` (Messages API では `thinking` のブロック) に、JSON は答えに入ります。エンジンは
  答えに少なくとも 256 token を残すように思考を閉じます。そのため思考ありでは `max_tokens` (Responses API では `max_output_tokens`) が 545 以上要り、
  それより小さいと 400 で断ります。短い返事なら、curl の例のように `"chat_template_kwargs": {"enable_thinking": false}` で思考を切ってください。
- **400 で断るもの。** 返事のヘッダより前に断ります (ストリーミングでも同じ)。どれも理由をメッセージで返します。
  - `tools` (空でない一覧) と一緒のとき、`tool_choice` が `required` か名前を指定した関数のとき: まだ対応していません。
  - `stop` の文字列 (JSON を途中で切りうるため) や `ignore_eos` と一緒のとき。
  - `MULTI` で起動したエンジン: まだ対応していません。
  - `regex`・`choice`・`grammar` (`guided_regex`・`guided_choice`・`guided_grammar`、`structured_outputs` の同じもの): まだ対応していません。
    `json_object` か `json_schema` を使ってください。
  - 文法が、書いてあるより緩くしか守れないスキーマ。サーバーは先にスキーマを確かめ、守っていない JSON を返す代わりに断ります: JSON Schema 2020-12
    以外の `$schema`。配列で書いた `items` や `additionalItems` (draft 4 のタプル。`prefixItems` で書いてください)。`#`・`#/$defs/NAME`・
    `#/definitions/NAME` 以外の `$ref`。`nullable` (OpenAPI のもの。`"type": ["integer", "null"]` と書いてください)。±2^53 を超える整数の範囲や定数。
    1〜65,536 の整数でも、小数点以下 8 桁までで小数点を除くと 65,536 以下の小数 (0.25、0.01) でもない `multipleOf`、1 つの値に 2 つの `multipleOf`。
    ほかのキーを許すオブジェクトの `minProperties`・`maxProperties`。`x-guidance` (サーバーが決めます)。64 KiB を超えるか、32 段より深いスキーマ。
    対になっていないサロゲート、NaN、Infinity。
- **知っておくこと。**
  - `properties` があって `additionalProperties` のないオブジェクトは、書いたキーだけを受け付けます (`allOf` の枝の中は除きます)。ほかのキーも
    許すなら `"additionalProperties": true` と書いてください。
  - `max_tokens` で切れた返事は `finish_reason` が `length` で、答えは終わっていない JSON です。読む前に `finish_reason` を確かめてください。
  - JSON に `\u` のエスケープは出ません。ほかの文字はそのまま書くので、キーの綴りは 1 通りです。短いエスケープ (`\n`、`\r`、`\t`、`\b`、`\f`)
    のない制御文字は書けません。token の間の空白は、改行 1 つまでと、空白かタブ 64 個までです。
  - 構造化のリクエストは drafter (MTP や DFlash2) なしで decode するので、同じ長さの普通のリクエストより遅くなります。普通のリクエストは前と同じで、
    r3.3.2-102 と同じ token、同じ速さです。
  - オフにするには、エンジン設定の「サーバー」の **構造化出力**、`docker run` の行の `-e STRUCTURED=0`、`glm53.conf` の `STRUCTURED=0` のどれかを使います。
    次の起動から効き、そのようなリクエストは 400 になります (`CONFIG.ja.md`)。最初のノードが `lib/libllguidance.so` を読み込めないときは、
    エンジンはそれなしで起動し (rank 0 のログに `structured output unavailable`)、同じ 400 になります。
  - スイッチの 8 台で確かめたこと: JSON のオブジェクトとスキーマ、思考あり、ストリーミング、`max_tokens` で切れたとき、クライアントが切ったストリーム、
    3 つの API、断るものすべて。どの後もすべての rank が動いていました。普通のリクエストは 20 の prompt で r3.3.2-102 と同じ token でした。

## 14. 同じ答えを出すモード

**何をするか。** `DETERMINISTIC=1` にすると、起動してから同じ要求を同じ順に送れば、起動し直しても同じ token が返ります
(同じ版・同じノード・同じ設定のとき)。温度によらず成り立ちます。`seed` のない要求には、どちらのモードでも prompt から seed を決めるので、
サンプリングした返事も同じになります。既定ではオフです。

**なぜあるか。** 既定では、起動ごとに変わりうるものが 2 つあります。エンジンは起動のたびに linear のカーネルのタイルを計って一番速いものを使い、
長い prompt の routed expert は計算の終わった順に結果を足します。どちらも数値の最後のビットを動かすことがあり、ときどき token が変わります。
2 つの設定を比べる、試験を繰り返す、返事を再現するには、同じ要求に同じ答えが要ります。

**使い方。** `glm53.conf` の `DETERMINISTIC=1`、`docker run` の行の `-e DETERMINISTIC=1`、エンジン設定の「サーバー」の
**同じ答えを出すモード** のどれかで、次の起動から効きます。`/health` は `"deterministic": true` を返し、chat と Responses の API では
各返事の `tensorfold` も同じです。その `token_sha` (返事の token のハッシュ) で、2 つの起動の返事を比べられます。

このモードでは、EXL3 の linear は計ったタイルでなく形で決まるタイルを使い、prompt の routed expert は各行の slot を届いた順でなく
slot の順に足して、fp16 の和は使いません。起動のときには、全ランクが設定・タイル・読み込んだライブラリ・NCCL の設定を照らし合わせ、
1 つでも違えば起動を止めます。スイッチでは、リングと同じく、NCCL を Ring のアルゴリズムと 2 チャネルで動かします。

- **制約。**
  - 会話は 1 つずつです。`MULTI` が 1 以上だと起動を断ります。起動画面は同時推論の 2〜4 を灰色にして、理由を出します。
  - モードが決めるものは `EXTRA_ENV` と `LAUNCH_ENV` に書けません。`TF_GLM53_TUNE`、`TF_GLM53_PE_F16`、`TF_GLM53_DETERMINISTIC`、`TF_EXL3_PROMPT_EXPERTS`、`NCCL_ALGO`、`NCCL_PROTO`、`NCCL_PAT_ENABLE`、`NCCL_NVLS_ENABLE`、`NCCL_MIN_NCHANNELS`、`NCCL_MAX_NCHANNELS` のどれかがあると起動を断ります。
    エンジン設定の画面も、このモードを同時推論 2 以上やこれらの名前と一緒には保存しません。
  - `CONTEXT_LENGTH` と `KV_SIZE` は設定のとおりに使います。空きメモリに合わせて context length を縮めたり、KV に残りを全部使ったりはしません
    (どちらもノードの空きメモリで変わるためです)。収まらなければ起動を止めます。
- **それでも変わるもの。**
  - ツール呼び出しの id は乱数で、毎回違います。
  - 同じ起動の中で、キャッシュから追い出された prompt をもう一度聞くと、1 回目と違う返事になることがあります。キャッシュのブロックの区切りで、
    prompt を計算する順が変わるためです。起動し直して同じ順に送れば、同じように違います。
- **費用** (スイッチの 8 台): prefill は約 2 割遅くなります (4K トークンで 3.31 s、通常は 2.75 s。40K で 29.1 s、通常は 23.6 s)。
  decode はほぼ同じです (45.3 と 45.9 tokens/s)。各ランクは prompt の expert のために 384 MiB 多く持ちます (`ROWS` 8,192・`SP_PARTS` 4。
  `SP_PARTS` 2 か `ROWS` 16,384 なら 768 MiB)。KV の計画はこれを含めて立てます。
- **確かめたこと** (それぞれ 2 回の起動で): スイッチ (8 台) では 23 の要求 (短いもの 12、4K と 40K の prompt、ツール、構造化 4、温度 1.0 で 4)
  の token が 23 本とも同じで、KV キャッシュも 232 か所の比較ですべて同じでした。リング (4 台) では 23/23 と 112/112 です。
  思考の中間整理、3 ターンの会話 (プールの続きと Byte Resume)、KV の追い出しは、MTP でも DFlash2 でも 13/13 で、冷えた状態からの起動でも同じでした。
