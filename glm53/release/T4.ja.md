# 4 台の DGX Spark で動かすフルサイズの GLM-5.3

リリース r2-102 は、フルサイズの GLM-5.3 を 8 台だけでなく 4 台の NVIDIA DGX Spark でも動かします。同じアーカイブ（`tensorfold-r2-102-linux-aarch64.tar.gz`）とランチャー（`tf-glm53`）が、`NODES` に 4 台を並べるとテンソル並列 4（GB10 1 基に 1 ランク）で動きます。Fiore-lab による TensorFold 1.0.2 の非公式な派生物で、TensorFold プロジェクトのリリースではありません。両方に共通すること（NCCL、ssh、各コマンド、drafter、会話のキャッシュ、障害時）は `RUNTIME.ja.md` にあります。このページには、4 台で違う点と、4 台構成の設定と測定値を書きます。

## 動き方

- テンソル並列 4、decode コンテキスト並列 2（2 ランクずつの 2 組。各ランクは KV キャッシュの位置を 1 つおきに持ちます）。
- プロンプトは 16,384 行のチャンクで読み、各チャンクを 4,096 行のシーケンス並列の部分 4 つで計算します。部分和は ring で集約し、routed expert は部分ごとに各 expert の重みを 1 回読んで復号し、その部分の全行に使います。
- KV キャッシュは 4 ビット（`KV=fp4`）: latent の 1 行に e2m1 のコード 512 個、16 個ごとの e4m3 のスケール、2 のべき乗の行スケールを持ちます。これは MiaAI-Lab の GLM-5.3 EXL3 on 3x DGX Spark プロジェクトにある、4 ビットの latent KV キャッシュの形式です。コードは 16 バイトの片ごとに、sm_121a で attention の転置読みが読む順に並べます。attention はこの行をそのまま共有メモリに置き、MMA の入力にするところで e4m3 にします。
- プロンプトの部分の routed expert のスロットの和は fp16 で足します（`TF_GLM53_PE_F16`、既定で有効）。
- 長い行の indexer の上位選び（top-k）は、順序語の上位 16 ビットを先に読みます（`TF_GLM53_TOPK16`、既定で有効）。

## 各ノードに要るもの（RUNTIME.ja.md に加えて）

- 1 つの RoCE v2 ネットワークにつながった DGX Spark 4 台（100 Gb/s のポート 1 つずつで足ります）。1 台目から他のノードへパスワードなしで ssh できること。
- 4 台用のチェックポイント（下記）を全ノードの同じパスに置くこと。ディスクは 344.6 GB（321 GiB）です。
- 起動前に各ノードで 115 GiB の空きメモリ（DFlash2 なしなら 112）。`free -g` の表示で数えます。

## 4 台用のチェックポイント

Hugging Face 上の Fiore-lab の EXL3 チェックポイント `fiore-lab/GLM-5.3-EXL3-4x-DGX-Sparks` です。88 ファイルで 344.6 GB、ほかに `SHA256SUMS` とモデルカード 3 つがあります。層 3〜77 の routed expert は混在で、使われ方の少ない 50 %（19,200 個のうち 9,600 個。エージェント作業、コーディング、Linux の操作、サーバーのセキュリティについての、日本語と英語の使用統計から選んだもの）を 3 ビット、残りを 4 ビットにしています。それ以外は 8 台用のチェックポイント `fiore-lab/GLM-5.3-EXL3-8x-DGX-Sparks` とバイト単位で同じで（MTP 層を含む）、expert は保存時の 8 ランク分割のままです。重みはそれ自身のライセンス（GLM-5.3 License）に従います。

Hugging Face CLI で一度だけダウンロードし（`python3 -m venv` には `python3-venv` パッケージが必要です）、RoCE ネットワーク経由で残りの 3 台にコピーします。

```sh
python3 -m venv ~/hf-cli && ~/hf-cli/bin/pip install -U huggingface_hub
D=~/models/GLM-5.3-EXL3-4x-DGX-Sparks
~/hf-cli/bin/hf download fiore-lab/GLM-5.3-EXL3-4x-DGX-Sparks --local-dir $D
for n in NODE2 NODE3 NODE4; do    # the other three addresses in NODES
  rsync -a --mkpath -e "ssh -c aes128-gcm@openssh.com" $D/ $n:$D/ &
done; wait
```

コピーを確認するには、全ノードで `cd ~/models/GLM-5.3-EXL3-4x-DGX-Sparks && sha256sum -c --quiet SHA256SUMS` を実行します。1 台あたり数分かかり、すべてのファイルが一致すれば何も出力しません（このディレクトリを配置した後なら、`./tf-glm53 verify` で全ノードを一度に確認できます）。`glm53.t4.conf.example` の `WEIGHTS` はこのディレクトリを指しています。

## 設定

4 台用の設定は `glm53.t4.conf.example` にあります。`glm53.conf` にコピーしてアドレス、ネットワーク名、パスを書き換え、RUNTIME.ja.md のとおりに起動します。

```sh
cp glm53.t4.conf.example glm53.conf    # nodes, network names, NCCL, weights, drafter, port
./tf-glm53 deploy                      # the same directory on the other three nodes
./tf-glm53 up                          # checks, starts the ranks, waits, runs the smoke test
```

| 設定 | 値 | 意味 |
|---|---|---|
| `NODES` | アドレス 4 つ | ランク 0 が先頭 |
| `WEIGHTS` | `~/models/GLM-5.3-EXL3-4x-DGX-Sparks` | 4 台用のチェックポイント |
| `DCP` | 2 | decode コンテキスト並列 |
| `ROWS` / `SP_PARTS` | 16384 / 4 | プロンプトのチャンクの行数、チャンクあたりの部分の数 |
| `CONTEXT` | 737280 | 1 件のリクエストが到達できる位置の数（プロンプト + 応答） |
| `STORE` | 100000 | 以前の会話のために `CONTEXT` に加えて保持する位置の数 |
| `CACHE` | `pool` | KV プール（下記） |
| `KV` | `fp4` | 4 ビットの KV キャッシュ |
| `DRAFTER_KIND` | `mtp`（既定）または `dflash2` | 下の「drafter とライセンス」を参照 |

## リクエスト間で保持する会話

4 台では、会話を KV プール（`CACHE=pool`）に保持します。プールの仕組みは RUNTIME.ja.md にあります。上の値では、`CONTEXT` + `STORE` = 837,280 位置を 256 位置のブロックで持ち、すべての会話で共有します。

- リクエストは、直前の会話に限らず、どの会話であれキャッシュにある最も長い一致部分（prefix）から再開します。
- 同じように始まる会話（同じシステムプロンプト）は、共通のブロックを 1 回だけ持ちます。
- プールがいっぱいになると、最も長く使われていない会話から、末尾のブロックを返します。
- DFlash2 では、最大 8 件の会話の drafter の状態を保持します（`DRAFT_SAVES`）。

DFlash2 での空きメモリの最低は、512K のときに 1 ノードあたり約 3.2 GiB でした。同じ値のスロットキャッシュ（`CACHE=slots`）より約 0.5 GiB 少なくなります。

## 速度

**全ノードで GPU クロックを 2.1 GHz（2,100 MHz）に制限して測定しています**。キャッシュに一致部分のないコーディング用のプロンプト、リクエストは一度に 1 件（reasoning effort low、応答は最大 4,000 トークン）、上の設定です。2 回の測定の中央値です。

| プロンプト | 最初のトークンまでの時間、MTP / DFlash2（s） | MTP での decode（tokens/s） | DFlash2 での decode（tokens/s） |
|---|---|---|---|
| 129,438 トークン（128K） | 120.1 / 121.9 | 35.3 | 42.9 |
| 260,227 トークン（256K） | 253.3 / 256.9 | 33.2 | 40.7 |
| 529,885 トークン（512K） | 565.4 / 571.5 | 32.2 | 37.8 |

703,916 トークンの会話をもう一度送ると、プールから 703,899 位置を再開し、最初のトークンまで 3 秒未満でした。間に別の会話の短い質問を挟んだ後も同じです。

## 精度

公式の BF16 モデル（公式の重みを公式実装で動かし、FP32 で計算したもの）の出力分布に対する KL ダイバージェンスです。基準データの 8,192 トークンの窓 4 つについて位置範囲ごとに、決定的な構成で、このチェックポイントと 4 ビットの KV キャッシュを使って測りました。

| 位置 | 4 ビットの KV キャッシュ（この構成） | 8 ビットの KV キャッシュ |
|---|---|---|
| 1,024〜2,047 | 0.0190 | 0.0156 |
| 2,048〜4,095 | 0.0316 | 0.0258 |
| 4,096〜6,143 | 0.0289 | 0.0259 |
| 6,144〜8,190 | 0.0192 | 0.0160 |

- 混在のチェックポイントと 4 ビットの KV キャッシュは、重みとキャッシュそのものの近似です。別に測ると、混在は、全 expert を 3 ビットにしたチェックポイントが 4 ビット版に対して増やす分の 36〜58 % を増やし、4 ビットの KV キャッシュは 8 ビットに対して 0.003〜0.005 増やします。
- 4 台構成の高速化は、fp16 のスロットの和を除いて、どれも使わない場合と同じビットを出します。基準データの窓に対するランク 0 の logits（決定的な構成、ring と reduce-scatter、KV 4 ビットと 8 ビット）の MD5 が、それぞれを使う場合と使わない場合で同じです。上位選びは 131,072 トークンの teacher forcing でも同じです。
- fp16 のスロットの和で KL ダイバージェンスは変わりません: 0.0161 / 0.0239 / 0.0244 / 0.0166、fp32 の和では 0.0167 / 0.0234 / 0.0252 / 0.0172（同じ窓、8 台用のチェックポイント、KV 4 ビット）。

## drafter とライセンス

4 台でもどちらの drafter も動きます（RUNTIME.ja.md の「Drafter」の節）。

- `mtp`（既定）: チェックポイント自身の MTP 層です。GLM-5.3 の重みの一部で、そのライセンスに従います。
- `dflash2`: `incoai/GLM-5.3-DFlash2`。同梱していません。モデルカードのライセンスは CC BY-NC-ND 4.0（非営利・改変禁止）で、用途は研究と評価、商用ライセンスは Inco AI から得られます。入手と使い方は RUNTIME.ja.md を見てください。その運用が許諾の範囲にあるかは、運用する側が判断してください。

## 制限

- 1 件のリクエストが到達できるのは、プロンプトと応答を合わせて最大 `CONTEXT` 位置です。733,226 トークンのプロンプトなら、応答に残るのは約 4,000 トークンです。
- リクエストは一度に 1 件です（RUNTIME.ja.md のとおり）。
- 4 台では他に何も動かさないでください。メモリはこのサーバーだけで見積もっています。
